# 0. この文書の位置づけ

`doc/12_データベース構造レビュー資料.pptx` では、データベース設計の論点を「相談事項」として9件挙げた。
そのうち **有識者の判断を待たずに直すべきと結論できるもの** を、この文書に切り出して改修計画としてまとめる。

- 対象: 設計の意図に照らして**明らかに誤っている**、または**目的に対して機能していない**もの
- 対象外: 設計判断の分岐(customers 35列の分割単位、業務データ平文化の前提、監査を入れる時期など)。これらは `doc/12` の相談事項に残す
- 前提: **運用開始前**であり、既存データを引き継がない。破壊的変更が可能(`doc/09` 1.3節の方針を踏襲)
- マイグレーションは前方適用のみ(down を持たない)。既存の `0000`〜`0007` に続けて `0008`〜 を追加する

## 0.1 「相談不要」と判定した基準

次のいずれかに当てはまるものだけを収録した。

1. **自己矛盾している** — 自分たちのドキュメントが定めた方針と、実装が食い違っている
2. **すでに壊れている** — 意図した動作をしていないことを、コードを読んで確認できた
3. **DBに書いたつもりの制約が存在しない** — TypeScript の型だけで、データベースは何も検証していない
4. **目的に対して機能しない形になっている** — 集計・検索・計算に使うと宣言した値が、その用途に使えない型で入っている

判断が要るのは「どう直すか」ではなく「直すかどうか」であり、上記4つはいずれも「直す」以外の答えが無い。

# 1. ご質問への回答 — 勤怠のJSONと金額の文字列は設計ミスか

## 1.1 金額を文字列型で持っていること → **設計ミス**

`doc/07_技術構成提案書.md` 第6章に、自分たちで次のように書いている。

> 金額は常に整数(銭単位)で保持し、浮動小数は使わない。

にもかかわらず `receipts.amount` は `text` である。方針と実装が食い違っており(基準1)、
かつ「集計・請求に使う」と宣言した値が集計できない形で入っている(基準4)。**議論の余地なく直すべき。**

## 1.2 勤怠をJSON 1列に持っていること → **「JSONにしたこと」は妥当。ただし中身の作りは設計ミス**

切り分けが必要なので、3点に分けて判定する。

| 論点 | 判定 | 理由 |
|---|---|---|
| 1日分を `jsonb` 1列で持つこと | **妥当** | 常に1日分をまるごと読み書きする用途しかなく、`UNIQUE(tenant_id, staff_id, business_date)` で1行が特定できる。分解しない利点はある |
| キーがスプレッドシートの列記号(`C`/`D`/`AG`…) | **設計ミス** | 下記1.2.1 |
| 時刻・距離・分数を文字列で持つこと | **設計ミス** | 金額と同じ理由。計算に使う値が計算できない型で入っている(基準4) |

### 1.2.1 列記号キーが設計ミスである理由

`packages/core/src/domain/attendance/types.ts` のコメントは、この選択の理由をこう説明している。

> GAS版・webapp-poc版と全く同じキー名にしておくことで、実データを使った数値照合
> (このオブジェクトをそのまま両実装に渡して出力を比較する)が row_data の変換なしにできる

**理由自体は正当だが、手段の選び方が誤っている。** 照合は「変換関数1本を通す」だけで成立するので、
**そのために永続データの表現を犠牲にする必要が無い**(第3章 B項に具体案を示す)。
一時的な検証手段(Phase 7の実データ突き合わせ)のために、給与に直結する永続データの構造を
スプレッドシートの列レイアウトに固定してしまっている。

そして、その代償は照合が終わったあとも残る。

- **意味がデータベースから読めない** — `"AG"` が何かを知るにはアプリのコードを読むしかない。社労士や監査への説明もできない
- **訪問3件・事務作業2件が上限として固定されている** — `C/D/E`(#1)・`L/M/N`(#2)・`U/V/W`(#3)しか枠が無い。1日4件訪問した日を表現できない。これはスプレッドシートのテンプレート由来の制約が、データモデルの制約に化けたもの
- **元テンプレートの列構成に縛られる** — 様式が変われば、過去データのキーの意味が変わる

「JSONを使ったこと」ではなく「JSONの中身をスプレッドシートの座標で表したこと」が問題である。

# 3. 各項目の詳細

## A. 金額を整数列にする(P1・破壊的)

### 現状

```
receipts.amount        text     -- "1,000" や "1000円" のような文字列
receipts.dedupe_key    text     -- 正規化済み文字列(スタッフ・顧客・日時・金額・店舗名)
```

### 何が問題か

- `"1,000"` と `"1000"` が別の値になり、`SUM()` が使えない。月次の経費集計ができない
- `"1000円"` のような値も、データベースは無検証で受け入れる
- `doc/07` 第6章の請求機能(`invoice_lines`)は整数前提。いま請求機能を載せると、文字列→整数の変換を請求側で毎回やることになる

### 変更後

```sql
-- 0011_receipt_amount_integer.sql
ALTER TABLE "receipts" ADD COLUMN "amount_yen" integer;
ALTER TABLE "receipts" ADD COLUMN "amount_raw" text;
ALTER TABLE "receipts" DROP COLUMN "amount";
ALTER TABLE "receipts" ADD CONSTRAINT "receipts_amount_yen_nonneg"
  CHECK ("amount_yen" IS NULL OR "amount_yen" >= 0);
```

- `amount_yen integer` … 集計・請求に使う正の値。OCRが読めなかった場合は `NULL`
- `amount_raw text` … OCRが返した生の文字列。人が後から直すときの参照用に残す

### 影響するコード

| 場所 | 変更内容 |
|---|---|
| `packages/db/src/schema/receipts.ts` | 列定義の差し替え |
| `packages/core/src/usecases/receipts.ts` | `amount` の組み立てを `amount_yen` / `amount_raw` の2値に分ける |
| `packages/core/src/domain/reports/receiptDedupe.ts` | **変更しない**(下記の注意) |
| `packages/core/src/ports/repositories.ts` | `ReceiptRecord` の型 |
| `packages/integrations/src/gas-bridge/…` | スプレッドシートへ書く値を `amount_yen` から整形 |

### 注意 — 重複判定キーは触らないこと

`dedupe_key` は GAS版 `buildKey` と完全に同一の文字列でなければ、移行期に同じ領収書を重複と判定できない。
`normalizeAmount()`(`"1,000"` → `"1000"`)の出力を使い続ける必要がある。

したがって **`dedupe_key` は従来どおり正規化済み文字列から作り、`amount_yen` は集計専用に併存させる**。
`amount_yen` を `dedupe_key` の材料に使い替えてはいけない。

### 変換規則

```ts
// normalizeAmount() は "1,000" → "1000"、数値化できなければ生文字列を返す
const normalized = normalizeAmount(input.amount);          // dedupe_key 用(既存のまま)
const n = Number(normalized);
const amountYen = Number.isFinite(n) ? Math.round(n) : null; // 集計用
const amountRaw = normalizeText(input.amount) || null;       // 生値の保管
```

小数が来た場合は四捨五入して `amount_yen` に入れ、元の表記は `amount_raw` に残す(円未満の端数は業務上発生しない想定だが、
OCRの誤読で発生しうるため落とさない)。

### リスクと検証

- リスク: 低。領収書は挿入のみで更新経路が無く、既存データも引き継がない
- 検証: `SUM(amount_yen)` が期待どおりになるテストと、`dedupe_key` が従来と1文字も変わらないことを固定する既存テストの継続

## B. 勤怠 `row_data` を意味のあるキー・数値にする(P1・データ形式の破壊的変更)

### 現状

```jsonc
// attendance_days.row_data (jsonb)
{ "C": "○○様宅", "D": "9:00", "E": "12:00", "H": "20", "I": "雨",
  "L": "△△様宅", "M": "13:00", "N": "15:00", …, "AG": "4.2", "AN": "1", "AO": "備考" }
```

キーはスプレッドシートの列記号。値はすべて文字列。訪問は3件・事務作業は2件が枠の上限。

### 何が問題か

第1.2.1節に記載。要点は「意味が読めない」「訪問4件の日を表現できない」「計算に使う値が文字列」。

### 変更後(段階1 — 表現だけ直す。計算ロジックは触らない)

`jsonb` 1列という形は維持し、中身の表現だけを変える。

```jsonc
{
  "visits": [
    { "place": "○○様宅", "start": "09:00", "end": "12:00",
      "weatherAfter": "雨", "plannedMoveMin": 20, "distanceKm": 4.2 },
    { "place": "△△様宅", "start": "13:00", "end": "15:00",
      "weatherAfter": "", "plannedMoveMin": 0, "distanceKm": 2.8 }
  ],
  "officeWork": [ { "start": "16:00", "end": "17:00" } ],
  "commuteDistanceKm": 3.1,
  "returnDistanceKm": 3.4,
  "shoppingErrandCount": 1,
  "note": "備考"
}
```

- **配列にすることで訪問3件・事務2件の上限が外れる**(様式変更にも耐える)
- 分・km・件数は `number`。時刻は `"HH:mm"` 文字列を維持する
  - 時刻を `timestamptz` にしないのは、`business_date` と組み合わせれば日時が一意に決まり、
    日跨ぎ勤務も `end < start` で表現できるため。1日分をまるごと扱う設計と整合する
  - ただし形式の検証は必須(下記)

```sql
-- 0012_attendance_row_data_shape.sql
ALTER TABLE "attendance_days" ADD CONSTRAINT "attendance_days_row_data_object"
  CHECK (jsonb_typeof("row_data") = 'object');
```

`jsonb` の中身までDBで縛るのは現実的でないため、**アプリ境界で Zod により検証する**
(`packages/api/src/routes/attendance.ts` と `packages/ingestion`)。
「DBが検証できない」という弱点は残るが、少なくとも「どの形が正しいか」がスキーマとして1か所に書かれる状態になる。

### 計算ロジックを守るための変換アダプタ

`packages/core/src/domain/attendance/attendanceCalc.ts` は、**GAS版との数値一致を19ケースで検証済みの唯一の資産**である。
ここを書き換えると、その保証が揺らぐ。したがって計算ロジックは列記号のまま内部実装として温存し、境界に変換関数を2本置く。

```
[API / DB]  AttendanceRowData(意味のあるキー)
                 │  toColumnRow()      ← 計算・GASミラー・実データ照合で使う
                 ▼
[内部]      AttendanceColumnRow(C/D/E… 列記号。attendanceCalc.ts の入力)
                 │  fromColumnRow()    ← GAS版の実データを取り込むときに使う
                 ▼
[API / DB]  AttendanceRowData
```

- `toColumnRow()` … Phase 7 の実データ照合と、スプレッドシートへのミラー書き込みで使う
- `fromColumnRow()` … 既存テストの合成データ19ケースをそのまま流用するために使う

**これにより「照合のためにDBのキー名を犠牲にする」必要が無くなる。** 照合は変換関数1本で成立する。

### 影響するコード

| 場所 | 変更内容 |
|---|---|
| `packages/core/src/domain/attendance/types.ts` | `AttendanceRowData` を新形式へ。`AttendanceColumnRow` を内部型として分離 |
| `packages/core/src/domain/attendance/`(新規) | `toColumnRow()` / `fromColumnRow()` の追加 |
| `attendanceCalc.ts` | **変更しない**(入力型の名前だけ `AttendanceColumnRow` に) |
| `packages/core/src/usecases/attendance.ts` | 保存前の Zod 検証、計算前の `toColumnRow()` 適用 |
| `packages/api/src/routes/attendance.ts` | リクエストの検証スキーマ |
| `packages/integrations/src/gas-bridge/` | ミラー送信時に `toColumnRow()` を通す |
| `attendance.test.ts` / `testDoubles.ts` | 合成データを `fromColumnRow()` 経由に |

### リスクと検証

- リスク: 中(変更範囲は広いが、数値計算の中核は触らない)
- 検証: 既存の勤怠計算テスト19ケース+月次集計が、値を1つも変えずに通ること。
  加えて `fromColumnRow(toColumnRow(x)) === x` の往復テストを追加する

### 段階2(Phase 7 の実データ照合が終わったあと)

`jsonb` をやめ、明細テーブルへ正規化する。方向は明らかだが、実施は**照合の基準を動かさないため照合後**にする。

```sql
attendance_segments(
  tenant_id, id, attendance_day_id, seq,
  kind          text     -- 'visit' | 'office'
  place         text,
  start_time    time,
  end_time      time,
  weather_after text,
  planned_move_min integer,
  distance_km   numeric(6,2),
  UNIQUE (tenant_id, attendance_day_id, seq),
  FOREIGN KEY (tenant_id, attendance_day_id) REFERENCES attendance_days (tenant_id, id)
)
```

これにより「残業が多い月」「訪問距離の集計」がSQLで書ける状態になる。
`attendance_days` 側には日次の値(出勤・退勤距離、買物代行、備考)を数値列で残す。

## C. 主要な検索経路にインデックスを張る(P1・追加のみ)

### 現状

PostgreSQL は**外部キーの参照する側に索引を自動作成しない**。現在インデックスが1本も無いテーブルがある。

| テーブル | 現在のインデックス |
|---|---|
| `daily_reports` | 主キーのみ |
| `accident_reports` | 主キーのみ |
| `family_members` | 主キーのみ |
| `receipts` | `(tenant_id, dedupe_key)` の部分一意のみ |
| `sessions` | `(token_hash)` の一意のみ |

### 何が問題か

アプリの主要な読み取り経路が、すべて全件走査になる。

| コード | 実行されるクエリ | 現状 |
|---|---|---|
| `dailyReportRepository.listByCustomer` | `WHERE customer_id=? AND occurred_at<? ORDER BY occurred_at DESC LIMIT n` | 全行走査+ソート |
| `accidentReportRepository`(顧客の履歴) | 同様 | 全行走査+ソート |
| `familyMemberRepository.listByCustomer` | `WHERE tenant_id=? AND customer_id=?` | 全行走査 |
| `sessionRepository.deleteAllForStaff` | `DELETE WHERE tenant_id=? AND staff_id=?` | 全行走査 |

`listByCustomer` は「顧客の日報履歴」を開くたびに呼ばれる、最も頻度の高い読み取りである。
件数が少ないうちは体感できないが、日報は毎日積み上がる追記型のデータなので、放置すれば必ず遅くなる。

### 変更後

```sql
-- 0008_add_missing_indexes.sql
CREATE INDEX "daily_reports_tenant_customer_occurred_idx"
  ON "daily_reports" USING btree ("tenant_id", "customer_id", "occurred_at" DESC);
CREATE INDEX "accident_reports_tenant_customer_occurred_idx"
  ON "accident_reports" USING btree ("tenant_id", "customer_id", "occurred_at" DESC);
CREATE INDEX "family_members_tenant_customer_idx"
  ON "family_members" USING btree ("tenant_id", "customer_id");
CREATE INDEX "sessions_tenant_staff_idx"
  ON "sessions" USING btree ("tenant_id", "staff_id");
CREATE INDEX "receipts_tenant_customer_timestamp_idx"
  ON "receipts" USING btree ("tenant_id", "customer_id", "receipt_timestamp" DESC);
```

`occurred_at DESC` を索引に含めるのは、`ORDER BY occurred_at DESC LIMIT n` を並べ替えなしで返せるようにするため。

スタッフ側(`(tenant_id, staff_id)`)の索引は、日報・事故報告・領収書については当面不要
(スタッフで絞る画面が無い)。「スタッフ別の実績」を作る段階で追加する。

### リスクと検証

- リスク: なし。追加のみで、既存の動作を変えない
- 検証: `EXPLAIN` で `Seq Scan` が `Index Scan` に変わることを確認する。
  リポジトリ層のテストは実PostgreSQLに対して行っていないため(`doc/12` 問題⑤)、
  当面は手動の `EXPLAIN` 確認とし、結果をこの文書に追記する

## D. 値域をDBの CHECK 制約で縛る(P1・追加のみ)

### 現状 — 「制約を書いたつもり」になっている箇所がある

`packages/db/src/schema/outbox.ts` は、状態をこう書いている。

```ts
status: text({ enum: ['pending', 'processing', 'done', 'failed'] }).notNull().default('pending'),
```

**この `enum` は Drizzle の TypeScript 上の型付けにすぎず、データベースには CHECK 制約が生成されない。**
`packages/db/drizzle/*.sql` を全文検索しても CHECK 制約は1件も存在しない。
つまり `psql` から `status='でたらめ'` を書けるし、書けばワーカーが永久に拾わない行になる。

さらに悪い例が `accident_reports.report_type` である。

```
スキーマのコメント: '事故報告' | 'ヒヤリハット'
TypeScript の型:    string          ← union になっていない
入口(API)の検証:    typeof body.reportType === 'string' ← 値域を見ていない
データベースの制約: なし
```

**3層すべてで値域を検証していない。** クライアントが任意の文字列を送れば、そのまま保存され、
スプレッドシートにも書き出される。

`daily_reports.risk_rating` / `es_rating` も「1〜5」とコメントにあるが、`-999` を保存できる。

### 変更後

```sql
-- 0009_add_check_constraints.sql
ALTER TABLE "outbox_jobs" ADD CONSTRAINT "outbox_jobs_status_check"
  CHECK ("status" IN ('pending', 'processing', 'done', 'failed'));
ALTER TABLE "outbox_jobs" ADD CONSTRAINT "outbox_jobs_kind_check"
  CHECK ("kind" IN ('attendance_day', 'attendance_aggregate', 'daily_report',
                    'accident_report', 'receipt'));
ALTER TABLE "outbox_jobs" ADD CONSTRAINT "outbox_jobs_attempts_check"
  CHECK ("attempts" >= 0);

ALTER TABLE "accident_reports" ADD CONSTRAINT "accident_reports_report_type_check"
  CHECK ("report_type" IN ('事故報告', 'ヒヤリハット'));
```

## E. `updated_at` をDBトリガーで更新する(P1・追加のみ)

### 現状 — すでに壊れている

更新日時はアプリのコードが毎回セットする方針で、データベースのトリガーは無い。
そして **`customers` では実際にセットされていない**。

```
packages/db/src/repositories/customerRepository.ts
  update()      … patch の列だけを SET する。updated_at を含めない
  deactivate()  … deactivated_at だけを SET する。updated_at を含めない
  → ファイル全体を検索しても updatedAt という文字列が1つも無い
```

つまり `customers.updated_at` は**行を作った時刻で永久に止まっている**。
「最終更新日時」として画面や分析で使えば、そのまま誤った値になる。

### さらに危険な点 — ミラーの取り残しにつながる

スプレッドシートへの書き戻しジョブの冪等キーは、更新時刻から作っている。

```ts
// packages/core/src/domain/mirror/idempotencyKey.ts
buildMirrorIdempotencyKey(kind, targetId, revision)  // revision = record.updatedAt
```

`daily_reports` / `accident_reports` / `attendance_days` は現在きちんと `updated_at` をセットしているので
**今は動いている**。しかし今後 UPDATE 経路を追加したときに書き忘れると、冪等キーが前回と同一になり、
`UNIQUE(tenant_id, idempotency_key)` に弾かれて **ジョブが積まれず、編集内容がスプレッドシートへ永久に反映されない**。
しかもエラーにならないため気づけない。`customers` で実際に起きている書き忘れが、
より危険な場所で再発しうる状態になっている。

### 変更後

```sql
-- 0010_updated_at_trigger.sql
CREATE OR REPLACE FUNCTION "set_updated_at"() RETURNS trigger AS $$
BEGIN
  NEW."updated_at" = now();
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER "customers_set_updated_at" BEFORE UPDATE ON "customers"
  FOR EACH ROW EXECUTE FUNCTION "set_updated_at"();
-- 以下も同様に作成する
--   staff / daily_reports / accident_reports / family_members
--   attendance_days / app_settings / tenant_keys / outbox_jobs
```

`updated_at` を持つ9テーブルすべてに張る(`receipts` / `sessions` / `password_reset_codes` は
`created_at` のみで更新経路が無いため対象外)。

### 副作用と扱い

- トリガーが常に `now()` を入れるため、**アプリから `updated_at` を明示指定しても上書きされる**。
  これは意図した挙動(唯一の真実をDBに置く)。既存の `.set({ updatedAt: new Date() })` は残しても害はないが、順次削除してよい
- `outbox_jobs.updated_at` は「処理中のまま放置された行の回収判定」に使っている。
  トリガー化しても意味は変わらず、むしろ更新漏れが無くなる

### 書き忘れをCIで落とす

この改修は「トリガーの張り忘れ」という新しい書き忘れの種を作る。
プロジェクトの既存方針(`packages/db/src/rlsPolicies.test.ts` が RLS の張り忘れを検出する)に合わせ、
**`updated_at` 列を持つテーブルすべてにトリガーが存在することを検査するテストを追加する**。

### リスクと検証

- リスク: 低。PGlite で plpgsql トリガーが動作することを実機確認済み(第2.1節)
- 検証: `UPDATE` 後に `updated_at` が進むこと、`customers` の編集で進むこと(現在の不具合の回帰テスト)

## F. 日付・時刻の文字列を日付型にする(P2・破壊的)

### 現状

| 列 | 型 | 中身 |
|---|---|---|
| `family_members.dob` | `text` | `"1990/1/28"`(正規化済み) |
| `accident_reports.target_dob` | `text` | `"yyyy/MM/dd"` |
| `daily_reports.start_time` / `end_time` | `text` | `"HH:mm"`。未入力は空文字 |

### 何が問題か

- 生年月日が日付型でないため、年齢の算出・年代別の集計がSQLでできない。`"1990/13/45"` も保存できる
- 日報の開始・終了時刻が文字列のため、滞在時間の集計ができない。`22:00`〜`01:00` の日跨ぎも計算できない
- `start_time` は `occurred_at`(= 訪問日 + 開始時刻)と**同じ情報の二重管理**になっている
  (`occurredAt = parseJstDateTime(reportDate, startTime)`)

### 変更後

```sql
-- 0013 の一部
-- 生年月日: 日付型にし、解析できなかった表記は raw に退避する
ALTER TABLE "family_members" ADD COLUMN "dob_date" date;
ALTER TABLE "family_members" ADD COLUMN "dob_raw" text;
ALTER TABLE "family_members" DROP COLUMN "dob";

ALTER TABLE "accident_reports" ADD COLUMN "target_dob_date" date;
ALTER TABLE "accident_reports" ADD COLUMN "target_dob_raw" text;
ALTER TABLE "accident_reports" DROP COLUMN "target_dob";

-- 日報の時刻: 開始・終了を時刻付きで持ち、文字列列を落とす
ALTER TABLE "daily_reports" ADD COLUMN "started_at" timestamptz;
ALTER TABLE "daily_reports" ADD COLUMN "ended_at" timestamptz;
ALTER TABLE "daily_reports" DROP COLUMN "start_time";
ALTER TABLE "daily_reports" DROP COLUMN "end_time";
ALTER TABLE "daily_reports" ADD CONSTRAINT "daily_reports_time_order"
  CHECK ("ended_at" IS NULL OR "started_at" IS NULL OR "ended_at" >= "started_at");
```

- `dob_raw` を併存させるのは、取込元が自由記述(`"1990.1"` のような不完全な表記)であり、
  解析できない値を捨てると情報を失うため。解析できたものだけ `dob_date` に入れる
- `started_at` / `ended_at` は **`NULL` を「未入力」として使う**(空文字との違いが型で表せる)。
  `occurred_at` は並べ替え用のキーとしてそのまま残す
- スプレッドシートへ書き戻す `"HH:mm"` 表記は、ミラー時に整形する(保存はしない)

### 影響するコード

`packages/core/src/domain/reports/types.ts` の `DailyReportContent`、`reports.ts` usecase、
`familyMembers` / `accidentReports` のリポジトリ、`parseFamilyInfo`、GASミラーの整形。

### リスクと検証

- リスク: 中(日報の本文構造に触る)
- 検証: 日跨ぎ勤務(`22:00`〜`01:00`)を保存・再取得できるテストを追加する。
  未入力が `NULL` として往復することを固定する

## G. 緯度経度を数値2列にする(P2・破壊的)

### 現状

```
customers.lat_lng  text  -- RESERVA CSVの「緯度・経度」列の文字列をそのまま保持
```

コードを追うと、この値は**どこでも解析されず、文字列のまま素通りしている**だけである
(`customerRepository` → `usecases/customers.ts` → 画面)。

### 何が問題か

`doc/07` と秘密保持契約(案)第4条は、この座標を使う前提を明記している。

- 仙台市への報告では**住所を座標化**して出す(第4条)
- 将来のジオフェンス機能(`doc/07` 第14章)
- 勤怠の移動距離計算

いずれも数値としての座標が必要で、`"38.26, 140.87"` のような1本の文字列では使えない。
「座標化して報告する」と決めているのに、座標が計算に使えない形で入っている(基準4)。

### 変更後

```sql
-- 0013 の一部
ALTER TABLE "customers" ADD COLUMN "lat" numeric(9, 6);
ALTER TABLE "customers" ADD COLUMN "lng" numeric(9, 6);
ALTER TABLE "customers" ADD COLUMN "lat_lng_raw" text;
ALTER TABLE "customers" DROP COLUMN "lat_lng";
ALTER TABLE "customers" ADD CONSTRAINT "customers_lat_range"
  CHECK ("lat" IS NULL OR "lat" BETWEEN -90 AND 90);
ALTER TABLE "customers" ADD CONSTRAINT "customers_lng_range"
  CHECK ("lng" IS NULL OR "lng" BETWEEN -180 AND 180);
```

`numeric(9,6)` は小数第6位(約10cm)まで保持でき、日本国内の座標に十分。
浮動小数(`double precision`)を避けるのは、金額と同じ理由で丸め誤差を持ち込まないため。

PostGIS の `geography` 型は、距離計算をDB側で行う段階になったら検討する(いまは過剰)。
`lat_lng_raw` は取込元の表記をそのまま残す用途。

### リスクと検証

- リスク: 低(現在どこでも計算に使っていないため、影響範囲が狭い)
- 検証: RESERVA CSVの実サンプル(`fixtures/`)から `lat` / `lng` が正しく取れることを取込テストで固定する

# 4.1 別枠 — 割引クーポンの適用記録(要望が確定したもの)

`doc/12` 相談⑧としていたクーポンは、**運用の実態を確認した結果この文書に含める**。

保留していた理由は「残枚数を列で持つか、使用履歴から算出するか」というモデリングの分岐だったが、
運用されているのは **1回の利用に対して割引を適用するクーポン(金額引き/率引き)だけ**で、
回数券(「10回券」のように枚数を発行して減らしていくもの)は無いことが確認できた。
枚数を持たないので分岐そのものが消え、判断が要らなくなった。

適用記録は **日報1件(サービス提供1件)に紐付ける**。領収書を日報の画面から登録している今の運用と
同じ粒度で追えるようにするため。

### 現状

クーポンを記録する場所が無い。日報の自由記述欄に書くしかなく、
「どのクーポンが何回使われたか」「今月いくら割引したか」を集計できない。

### 変更後 — 2テーブル

**種別マスタと適用記録を分ける。** 割引額はマスタ側にあるが、マスタを書き換えたときに
過去の適用記録の金額まで変わってしまってはいけないため、適用記録側に**適用時点の条件を写して持つ**
(請求に使う値なので、後から履歴が書き換わる形にはしない)。

```sql
-- 0014_coupons.sql
-- coupons: テナントごとに管理者が登録するクーポンの種別
CREATE TABLE "coupons" (
  "id"                   uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  "tenant_id"            uuid NOT NULL REFERENCES "tenants"("id"),
  "code"                 text NOT NULL,          -- 運用上の識別子(例 'INTRO500')
  "name"                 text NOT NULL,          -- 表示名(例 '紹介キャンペーン 500円引き')
  "discount_kind"        text NOT NULL,          -- 'amount' | 'percent'
  "discount_amount_yen"  integer,                -- amount のとき必須
  "discount_percent"     integer,                -- percent のとき必須(1〜100)
  "valid_from"           date,                   -- null は下限なし
  "valid_to"             date,                   -- null は無期限
  "active"               boolean NOT NULL DEFAULT true,
  "note"                 text,
  "created_at"           timestamptz NOT NULL DEFAULT now(),
  "updated_at"           timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT "coupons_tenant_code_uidx" UNIQUE ("tenant_id", "code"),
  CONSTRAINT "coupons_discount_kind_check"
    CHECK ("discount_kind" IN ('amount', 'percent')),
  -- 種別と値の組み合わせを縛る。片方だけ入れ替えて「率引きなのに金額が入っている」状態を作れない
  CONSTRAINT "coupons_discount_value_check" CHECK (
    ("discount_kind" = 'amount'  AND "discount_amount_yen" IS NOT NULL AND "discount_percent" IS NULL)
    OR
    ("discount_kind" = 'percent' AND "discount_percent" IS NOT NULL AND "discount_amount_yen" IS NULL)
  ),
  CONSTRAINT "coupons_discount_amount_yen_check"
    CHECK ("discount_amount_yen" IS NULL OR "discount_amount_yen" >= 0),
  CONSTRAINT "coupons_discount_percent_check"
    CHECK ("discount_percent" IS NULL OR "discount_percent" BETWEEN 1 AND 100),
  CONSTRAINT "coupons_valid_period_check"
    CHECK ("valid_to" IS NULL OR "valid_from" IS NULL OR "valid_to" >= "valid_from")
);

-- coupon_redemptions: 日報1件に対する適用記録(1件の日報に複数クーポンを適用できる)
CREATE TABLE "coupon_redemptions" (
  "id"                   uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  "tenant_id"            uuid NOT NULL REFERENCES "tenants"("id"),
  "daily_report_id"      uuid NOT NULL,
  "coupon_id"            uuid NOT NULL,
  "applied_at"           timestamptz NOT NULL DEFAULT now(),
  -- 適用時点のスナップショット(マスタの書き換えで過去の記録が動かないようにするため)
  "discount_kind"        text NOT NULL,
  "discount_amount_yen"  integer,
  "discount_percent"     integer,
  "note"                 text,
  "created_at"           timestamptz NOT NULL DEFAULT now(),
  "updated_at"           timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT "coupon_redemptions_tenant_daily_report_fk"
    FOREIGN KEY ("tenant_id", "daily_report_id") REFERENCES "daily_reports" ("tenant_id", "id"),
  CONSTRAINT "coupon_redemptions_tenant_coupon_fk"
    FOREIGN KEY ("tenant_id", "coupon_id") REFERENCES "coupons" ("tenant_id", "id"),
  -- 二重送信・二重クリックで同じクーポンが同じ日報に2回付くのを止める
  CONSTRAINT "coupon_redemptions_report_coupon_uidx"
    UNIQUE ("tenant_id", "daily_report_id", "coupon_id"),
  CONSTRAINT "coupon_redemptions_discount_kind_check"
    CHECK ("discount_kind" IN ('amount', 'percent')),
  CONSTRAINT "coupon_redemptions_discount_value_check" CHECK (
    ("discount_kind" = 'amount'  AND "discount_amount_yen" IS NOT NULL AND "discount_percent" IS NULL)
    OR
    ("discount_kind" = 'percent' AND "discount_percent" IS NOT NULL AND "discount_amount_yen" IS NULL)
  )
);

CREATE INDEX "coupon_redemptions_tenant_coupon_idx"
  ON "coupon_redemptions" USING btree ("tenant_id", "coupon_id");
```

いずれも `tenant_id` を持つので、他テーブルと同じく RLS(`tenant_isolation` + `FORCE`)を張る。

### 設計上の判断

| 論点 | 決定 | 理由 |
|---|---|---|
| クーポンを列(`daily_reports.coupon_code`)で持つか、テーブルにするか | **テーブル** | 1回の訪問に複数のクーポンを適用しうる。列だと1つしか持てず、あとから増やせない |
| 顧客ID を `coupon_redemptions` に持たせるか | **持たせない** | 日報から引ける。二重に持つと日報側の顧客と食い違う状態を作れてしまう |
| 割引後の請求額を保存するか | **保存しない** | 算定基礎(単価・時間)を持つ請求機能(`invoice_lines`)がまだ無い。無い値を列にしても埋まらない。導入時に、この2テーブルを入力として計算する |
| クーポンを廃止したときに行を消すか | **消さない**(`active=false`) | 過去の適用記録から参照されている。消すと履歴が壊れる |
| 適用記録に割引条件を写すか | **写す** | 請求に使う値なので、マスタの書き換えで過去の記録が動いてはいけない |

### リスクと検証

- リスク: 低。追加のみで、既存のテーブル・列には触らない
- 検証: 種別と値の組み合わせを縛る CHECK が実際に不正な組み合わせを拒否すること、
  同じ日報に同じクーポンを2回付けられないことを PGlite 上のテストで固定する

# 6. この文書で扱わないもの(判断が必要なもの)

次は `doc/12_データベース構造レビュー資料.pptx` の相談事項として残す。設計判断の分岐であり、
「明らかにこちらが正しい」と言えないため。

| 相談 | 論点 | この文書に入れなかった理由 |
|---|---|---|
| ① | `customers` 35列を分割するか | 顧客マスタとして35列が過大かは基準が要る。分割はJOINの増加と取込処理の複雑化という代償を伴う |
| ② | 業務データ平文化の前提 | 保存時暗号化を本番基盤に委ねる判断そのものの妥当性 |
| ⑤ | 廃棄・返還の手順 | スキーマではなく運用手順の設計 |
| ⑥ | 監査(pgaudit)と Cloud KMS の導入時期 | いつ入れるかは要件と時期次第 |
| ⑦ | 予約・請求を土台に入れる順番 | 要件が固まる前に作る是非 |
| ⑨ | 見落としているPostgreSQLの落とし穴 | 指摘いただく対象 |

相談⑧(クーポンのモデル)は、運用に回数券が無いことを確認して分岐が消えたため、第4.1章に取り込んだ。

なお **B項の段階2(勤怠の正規化)** は方向としては明らかだが、Phase 7 の実データ照合の基準を
動かさないため、照合完了後に実施する。
