パッケージ構成と依存の向き pnpm workspace / 9パッケージ

  • 矢印は「依存する方向」。逆流は1本もない(package.json で確認)
  • core は shared 以外に依存しない。DBドライバ・argon2・googleapis は全部外側
  • db / integrations は core のポートを実装する側。ここだけが外部SDKを知る
  • api は Hono のルートと Container(全ポートの束)の型。Node向けの組み立ては別ファイル
  • demo が api を依存に持つのは、ブラウザ内で同じ Hono アプリを動かすため

判断してほしい点

web → demo が dependencies(devではない)。本番ビルドへの混入は Vite プラグイン + CI の成果物検査の二重ガードで防いでいるが、構造としては脆い。

packages/*/package.jsonkatahimo-app
ヘキサゴナルを、パッケージ境界で強制している構成です。core は外部SDKを一切importしないので、ブラウザでもNodeでも同じコードが動きます。これがデモを可能にしている根拠でもあります。右下は自分から挙げる弱点で、web が demo を通常依存に持っている点です。

ヘキサゴナル: ポートとアダプタ core は「穴」だけを知る

  • 矢印は全部 core に向かって入る。core から外へ出る依存は無い
  • usecase は XxxDeps(必要なポートだけの構造的部分集合)を受け取る。Container をそのまま渡せる
  • Container = 全ポートの束。Node用 createContainer(env, db) と ブラウザ用 createDemoContainer() が同じ型を返す
  • 外部が無いときは Noop 実装に落ちる(Maps / Schedule / AI / Mirror)。黙って壊れない

マルチテナント分離 shared schema + tenant_id + RLS

  • テナント別スキーマ/DBは不採用: 「法人ごとにスキーマが分岐すると保守が破綻しやすい」(doc/07)
  • FKはRLSをバイパスする(PG仕様)→ 参照は (tenant_id, id) の複合FKに統一。参照先に UNIQUE(tenant_id, id)
  • アプリ側(withTenant)と DB側(RLS)の二重防御。片方が抜けても他方が止める

論点

  • FORCE は drizzle-kit が出力しないため、マイグレーション生成後に手で追記している。新テーブル追加時に忘れると所有者接続でRLSが素通り。CIで検出する仕組みは無い
  • tenants は唯一RLS対象外(ログイン前にslugで特定するため)。アプリロールが全テナント一覧を読める
packages/db/src/tenantScope.ts / schema/_rls.ts / drizzle/*.sql / infra/initdbkatahimo-app
分離は shared schema + RLS。アプリ側とDB側の二重防御です。判断してほしいのは右下の2点。FORCE の手動追記はプロセスリスクなので、たとえばマイグレーションSQLを検査するテストを足すべきか。tenants がRLS対象外である点は、ワーカーが全テナントを列挙する設計とも絡みます。

  • 復号監査は「誰が」を含まない。平文列へのアクセスは監査対象外

認証・認可 自前実装(提案書の Firebase Auth からは変更)

パスワード

  • argon2id(@node-rs/argon2、パラメータは既定値のまま)
  • GAS版の共有ソルト SHA-256 は、ログイン成功時にサイレント再ハッシュして移行(再設定を強いない)
  • 最低8文字のみ。記号・大文字の必須化はしない(付箋に書く動機を作らない)

セッション

  • 32B乱数トークン、DBには SHA-256 のみ。httpOnly / SameSite=Lax / 本番 Secure。TTL 7日(絶対期限)
  • getAuthenticatedSession が唯一の解決入口。WeakMap<Context> でリクエスト内キャッシュ
  • requirePasswordChangeGuard: 初期パスワードのまま他APIを叩くと403(ミドルウェア1箇所)

パスワード再設定(GAS版から意図的に変えた点)

  • 存在しない宛先でも同じ応答(ユーザー列挙を塞ぐ)。送信失敗も応答を変えない
  • 6桁コードは HMAC-SHA256(pepper, code) で保存。pepper は環境変数、DBに置かない
  • 検証と消費は SELECT … FOR UPDATE の1トランザクション。誤入力5回で無効、定数時間比較
  • 書き込みは replacePassword 1本: 行ロック → 差し替え → セッション破棄を同一tx。楽観ロック expect で「認証後に別経路が差し替えた」を弾く

論点

  • ログイン試行のレート制限が無い(再設定コードには5回制限があるのに非対称)
  • CSRF対策は SameSite=Lax のみ。CSRFトークン・Originチェック無し
  • SESSION_SECRET が必須なのにどこからも参照されていない(Cookieは署名していない。乱数トークン+DB照合なので設計上は不要という整理は可能)
  • 再設定コード消費とパスワード書き込みは別リポジトリ=別tx。残る失敗は「コード1枚が無駄になる」のみ
packages/core/src/usecases/{auth,passwordReset,staff}.ts / packages/api/src/session.tskatahimo-app
提案書では Firebase Auth でしたが、実装は自前です。GAS版のパスワードをそのまま移行できるようにしたかったのが理由です。右下の論点、特にログインのレート制限が無い点と、SESSION_SECRET が使われていない点は、レビュー前に自分で見つけたものです。どちらも直す方針ですが、優先度の判断をいただきたい。

1本のリクエストを追う 「日報を保存する」

論点: ポートの契約(MirrorPort.enqueue の doc)は「ドメイン書き込みと同一トランザクションで呼ぶこと」と書いてあるが、実装は別トランザクション(各リポジトリが自前で withTenant を開く)。①成功→②失敗でミラーが永久に欠落し、検知手段が無い。理由の記述はどこにも無い。
packages/core/src/usecases/reports.ts:77-112 / packages/db/src/repositories/outboxRepository.tskatahimo-app
1本追うとこうなります。黄色の線より上が同期、下がWorkerの非同期。赤いバッジが今日いちばん指摘されるであろう箇所で、Outboxパターンの本来の保証、つまり「ドメイン書き込みとジョブ登録の原子性」が実装では失われています。ポートのdocコメント自身が「同一トランザクションで」と書いているのに、実装が守っていない。直すには、リポジトリ横断でトランザクションを共有する仕組み(unit of work)が要ります。これは再設定コードの件でも同じ壁に当たりました。

GAS版との共存 正データは PostgreSQL、Sheets はミラー

  • 方針(doc/10): 新規GCP API より既存GASブリッジを優先。理由は ①新規課金・認証情報の準備を避ける ②GAS側の実証済みロジック(イベント分類・タグ解析・スタッフ名マッチ)を再実装しない
  • Sheets を止めるときは「ミラーのアダプタを止めるだけ」でドメインは無変更
  • 多重ワーカー安全(SKIP LOCKED)。未知の kind は例外 → failed

論点

  • Mail / Maps / Calendar / Sheets の4系統が1本のGAS Web Appに集中。SLA・クォータ・6分実行制限。タイムアウト20秒固定、リトライ無し
  • secret が URL クエリに載る(GASはヘッダーを読めない)。実行ログ・プロキシに残る。ローテーション手順なし
  • failed は終端。自動リトライ・バックオフ・DLQ 無し。attempts 列は未使用。processing で落ちた孤児の回収も無い
  • idempotencyKey が randomUUID() なので、UNIQUE 制約による冪等性はリトライ時に効かない

GASブリッジを既定にしたのは、新規GCP課金を避けつつ、現場で動いているロジックを捨てないためです。ただしこのブリッジは、実はまだ一度もデプロイされておらず、メール送信アクションは存在すらしません。つまりSheetsミラーとメールは「コードはあるが本番で動いたことがない」。加えてリトライが無い、secretがURLに載る、と運用面の穴が並びます。ここは設計の是非というより「この依存のしかたを許容するか」の判断です。

公開デモ 同じコードをブラウザ内で丸ごと動かす

  • デモの鍵は公開固定値 → 訪問者が入れた Gemini キー等は永続化しない(暗号化しても平文同然のため)

判断していただきたいこと 優先度順

1. トランザクション境界(構造の問題)

リポジトリが各自で withTenant(=tx)を開くため、複数リポジトリを跨ぐ書き込みが原子的にならない。Outbox の積み損ね、再設定コード消費とパスワード書き込みの分離、の2箇所で既に顕在化。

選択肢: (a) unit-of-work を導入し tx を usecase 側で開く (b) 「同一tx契約」を諦めて outbox を DB トリガ/CDC に寄せる (c) 現状を受容し監視で補う

2. GAS ブリッジ 1本への依存(運用の問題)

Mail / Maps / Calendar / Sheets を未デプロイの GAS Web App に集約。secret は URL クエリ、リトライ無し、failed は終端。

選択肢: この依存を許容し早期にデプロイ+運用設計するか、少なくともメールだけは別経路(SES/SendGrid等)にするか

3. 鍵管理の順序(いつ本番相当にするか)

Cloud KMS 未実装、DEK 1世代。インターフェースは差し替え可能な形だが、ローテーション不能な状態でデータを溜め始めてよいか。

4. RLS の担保をどこまで自動化するか

FORCE の手動追記、実DBでの RLS テスト無し。マイグレーションSQLの静的検査、または postgres-js での分離テストを CI に入れるべきか。

5. 認証のハードニング

ログインのレート制限、CSRF、argon2 パラメータ明示、未使用の SESSION_SECRET 整理、監査ログの「誰が」。どれをローンチ前提条件にするか。

いずれも「直せない」ものではなく「今直すべきか、いつ直すか」の判断katahimo-app
5つに絞りました。1番は構造の問題で、放置すると2箇所から3箇所、4箇所と増えるので、いま判断したい。2番は設計の是非より「この依存を許容するか」。3〜5は順序の問題です。私の推奨は、1番の unit-of-work を次に着手し、2番はメールだけ別経路に逃がすこと。ただしこれは意見なので、ご判断をいただきたい。

まとめ

この設計で守れていると考えているもの

  • core が外部SDKを知らない → Node とブラウザで同一コードが動く(デモで実証)
  • テナント分離の二重防御(withTenant + RLS/FORCE + 複合FK)
  • 要配慮データの列暗号化と、暗号学的削除の導線
  • 認証の失敗経路(列挙・総当たり・割り込み・部分更新)を塞いだ
