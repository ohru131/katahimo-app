パッケージ構成と依存の向き pnpm workspace / 9パッケージ

  • 矢印は「依存する方向」。逆流は1本もない(package.json で確認)
  • core は shared 以外に依存しない。DBドライバ・argon2・googleapis は全部外側
  • db / integrations は core のポートを実装する側。ここだけが外部SDKを知る
  • api は Hono のルートと Container(全ポートの束)の型。Node向けの組み立ては別ファイル
  • demo が api を依存に持つのは、ブラウザ内で同じ Hono アプリを動かすため

デモ用コードの隔離

web → demo は devDependencies。本番ビルドでは Vite プラグインが入口をスタブ化し、CI が成果物そのものを検査する(.wasm の有無と禁止文字列)。設定を読むのではなく出力を見るので、設定ミスでも素通りしない。

packages/*/package.jsonkatahimo-app
ヘキサゴナルを、パッケージ境界で強制している構成です。core は外部SDKを一切importしないので、ブラウザでもNodeでも同じコードが動きます。これがデモを可能にしている根拠でもあります。右下は自分から挙げる弱点で、web が demo を通常依存に持っている点です。

ヘキサゴナル: ポートとアダプタ core は「穴」だけを知る

  • 矢印は全部 core に向かって入る。core から外へ出る依存は無い
  • usecase は XxxDeps(必要なポートだけの構造的部分集合)を受け取る。Container をそのまま渡せる
  • Container = 全ポートの束。Node用 createContainer(env, db) と ブラウザ用 createDemoContainer() が同じ型を返す
  • 外部が無いときは Noop 実装に落ちる(Maps / Schedule / AI / Mirror)。黙って壊れない
  • UnitOfWorkPort だけは横断的で、複数リポジトリの書き込みを1つのトランザクションにまとめる(9枚目)

例外を1つ正直に

PasswordHasherPort だけ ports/ ではなく usecases/auth.ts に定義されている。動作に影響はないが、置き場所の一貫性は崩れている。

packages/core/src/{ports,usecases,domain} / packages/api/src/container.tskatahimo-app
教科書どおりのポート&アダプタです。強調したいのは「同じ Container 型を、Node とブラウザで別々に組み立てている」こと。デモはリポジトリも暗号化もusecasesも本番と同一コードで動きます。差し替えているのは、Node専用の実装と、鍵を置けない外部APIだけです。

マルチテナント分離 shared schema + tenant_id + RLS

  • テナント別スキーマ/DBは不採用: 「法人ごとにスキーマが分岐すると保守が破綻しやすい」(doc/07)
  • FKはRLSをバイパスする(PG仕様)→ 参照は (tenant_id, id) の複合FKに統一。参照先に UNIQUE(tenant_id, id)
  • アプリ側(withTenant)と DB側(RLS)の二重防御。片方が抜けても他方が止める

効いていることをCIで確かめている

  • 静的検査: スキーマから全テーブルを動的に集め、SQLに ENABLE と FORCE の両方、ポリシーの USING/WITH CHECK が揃っているかを検査。新テーブルで FORCE を書き忘れると落ちる
  • 実DB検証: PGlite上に非特権ロールを作り、他テナントの行が見えないこと・WITH CHECK で弾かれることを確認。FORCE 無しの比較用テーブルと挙動が変わることまで固定

残るトレードオフ

tenants は唯一RLS対象外(ログイン前にslugで特定するため)。アプリロールが全テナント一覧を読める。

packages/db/src/tenantScope.ts / schema/_rls.ts / drizzle/*.sql / infra/initdbkatahimo-app
分離は shared schema + RLS。アプリ側とDB側の二重防御です。判断してほしいのは右下の2点。FORCE の手動追記はプロセスリスクなので、たとえばマイグレーションSQLを検査するテストを足すべきか。tenants がRLS対象外である点は、ワーカーが全テナントを列挙する設計とも絡みます。

論点

  • Cloud KMS 実装は存在しない。KEK が環境変数1本のままなので、封筒暗号化の主要な便益(鍵の物理分離・KMS側監査)は未実現
  • 世代が並存するのでローテーションで既存データは壊れないが、再暗号化バッチが未実装。古い世代の鍵を捨てられない
  • 監査は認証イベントには「誰が」が入るが、復号は「どのテナント」まで。平文列(氏名・住所)へのアクセスはそもそもこの網に入らない
packages/integrations/src/local-crypto, local-kms / doc/09 3章katahimo-app
封筒暗号化の形は本番相当ですが、KEKがまだ環境変数です。「インターフェースを変えずにCloud KMSへ差し替える」設計なので構造は問題ないと考えていますが、現時点では本番相当の鍵管理が存在しない、とはっきり言っておきます。DEKローテーションが1世代しか扱えない点は、今のうちに直すべきか、ご意見をいただきたい。

認証・認可 自前実装(提案書の Firebase Auth からは変更)

パスワードとログイン試行

  • argon2id。コストは明示指定(m=19MiB, t=2, p=1)。既定任せにすると、どのコストで運用しているかがコードから読めない
  • GAS版の共有ソルト SHA-256 は、ログイン成功時にサイレント再ハッシュして移行(再設定を強いない)
  • 連続10回の失敗で15分ロック、成功でリセット。恒久ロックにしないのは、狙って失敗させれば人を締め出せてしまうため
  • ロック中かどうかで応答を変えない。変えると10回試すだけでアカウントの有無が分かる

セッション

  • 32B乱数トークン、DBには SHA-256 のみ。httpOnly / SameSite=Lax / 本番 Secure。TTL 7日(絶対期限)
  • Cookieに署名鍵は使わない。値は高エントロピーの乱数で、検証はDB側の照合。署名しても増える保証がない
  • 書き込み系は Origin 照合でクロスサイトを弾く(SameSite に加えたサーバー側の1枚)
  • requirePasswordChangeGuard: 初期パスワードのまま他APIを叩くと403(ミドルウェア1箇所)

パスワード再設定(GAS版から意図的に変えた点)

  • 存在しない宛先でも同じ応答(ユーザー列挙を塞ぐ)。送信失敗も応答を変えない
  • 6桁コードは HMAC-SHA256(pepper, code) で保存。pepper は環境変数、DBに置かない
  • 検証と消費は SELECT … FOR UPDATE の1トランザクション。誤入力5回で無効、定数時間比較
  • 書き込みは replacePassword 1本: 行ロック → 差し替え → セッション破棄を同一tx。楽観ロック expect で「認証後に別経路が差し替えた」を弾く

監査

ログインの成否・パスワード変更・再設定・管理者によるスタッフ操作を、誰が・誰を付きで構造化ログに残す。ログイン失敗だけ severity を上げ、総当たりの兆候をフィルタで拾えるようにしている。

論点

  • 絞り込みはアカウント単位のみ。IPや端末単位のレート制限は前段(WAF/Cloud Armor)が要る
  • レガシーの共有ソルト SHA-256 経路が残る。ログインしないスタッフのハッシュは期限なく残り続ける
  • セッションは絶対期限7日のみ。アイドルタイムアウト・同時セッション数の制限は無い
packages/core/src/usecases/{auth,passwordReset,staff}.ts / packages/api/src/session.tskatahimo-app
提案書では Firebase Auth でしたが、実装は自前です。GAS版のパスワードをそのまま移行できるようにしたかったのが理由です。右下の論点、特にログインのレート制限が無い点と、SESSION_SECRET が使われていない点は、レビュー前に自分で見つけたものです。どちらも直す方針ですが、優先度の判断をいただきたい。

要点: ドメインの行と outbox_jobs は同じトランザクションで確定する。片方だけ通ると、保存はできたのにスプレッドシートへ永久に反映されない行が、誰にも気づかれずに残る。暗号化・通知・名前解決はトランザクションの外に出してある(単一接続のPGliteで内側から別トランザクションを開くと止まるため)。
packages/core/src/usecases/reports.ts / ports/unitOfWork.ts / packages/db/src/unitOfWork.tskatahimo-app
1本追うとこうなります。緑の枠が1つのトランザクションで、日報の行とoutboxへの積み込みが揃って確定します。片方だけ成立する状態を作らないのが要点です。黄色の線から下がWorkerの非同期処理で、送信に失敗しても終端させず、バックオフして戻します。トランザクションの外に出してあるもの(暗号化・通知)には理由があって、単一接続のPGliteで内側から別のトランザクションを開くと自分の完了を待って止まるためです。テストでは、outboxへの書き込みだけを失敗させて日報の行が残らないことを固定しています。

GAS版との共存 正データは PostgreSQL、Sheets はミラー

  • 方針(doc/10): 新規GCP API より既存GASブリッジを優先。理由は ①新規課金・認証情報の準備を避ける ②GAS側の実証済みロジック(イベント分類・タグ解析・スタッフ名マッチ)を再実装しない
  • Sheets を止めるときは「ミラーのアダプタを止めるだけ」でドメインは無変更
  • 多重ワーカー安全(SKIP LOCKED)。processing のまま5分放置された行は再びclaim対象になる(ワーカーが落ちた場合の回収)
  • 失敗は終端にしない。5秒から倍々・上限1時間で再試行し、8回で failed。ワーカーはその件数を error ログに出す

論点

  • Mail / Maps / Calendar / Sheets の4系統が1本のGAS Web Appに集中。SLA・クォータ・6分実行制限。単一障害点であることは変わらない
  • secret が URL クエリに載る(GASはカスタムヘッダーを読めない)。実行ログ・プロキシに残る。ローテーション手順は未整備
  • そのGAS Web App がまだ一度もデプロイされていない。sendEmail アクションはGAS側に存在しない
  • デッドレターに落ちた分の再投入は手作業。管理画面からの操作は用意していない
packages/core/src/ports/mirror.ts / usecases/mirrorWorker.ts / packages/integrations/src/gas-bridgekatahimo-app
GASブリッジを既定にしたのは、新規GCP課金を避けつつ、現場で動いているロジックを捨てないためです。ただしこのブリッジは、実はまだ一度もデプロイされておらず、メール送信アクションは存在すらしません。つまりSheetsミラーとメールは「コードはあるが本番で動いたことがない」。加えてリトライが無い、secretがURLに載る、と運用面の穴が並びます。ここは設計の是非というより「この依存のしかたを許容するか」の判断です。

公開デモ 同じコードをブラウザ内で丸ごと動かす

判断していただきたいこと 優先度順

1. GAS ブリッジ 1本への依存

メール・地図・予定・スプレッドシートの4系統を、1つの GAS Web App に集約している。実行時間制限とクォータを持ち、SLA は無く、secret は URL クエリに載る。しかもまだ一度もデプロイしていない。

選択肢: (a) この依存のまま早期にデプロイして運用設計を詰める (b) メールだけ別経路(SES/SendGrid等)に逃がす (c) Sheets 連携そのものを移行の対象から外す

2. 鍵管理を本番相当にする時期

封筒暗号化の形はできていて世代も並存するが、KEK は環境変数のまま。Cloud KMS を入れる前に本番データを溜め始めてよいか。再暗号化バッチも未実装で、古い世代の鍵をまだ捨てられない。

3. 予約・請求・カルテをどう積むか

提案書の差別化要因は、まだスキーマにも無い。二重予約防止(EXCLUDE USING gist)や請求の整合性は、後から足すと既存データの移行が要る。いま土台に入れるか、後回しにするか。

4. テストの薄い層をどこまで埋めるか

ドメインとusecaseは厚いが、APIルート・実PostgreSQL・画面は手動確認のまま。どれをローンチ前提条件にするか。特に勤怠は給与に直結する。

5. 単一障害点と運用の受け皿

デッドレターの再投入、outbox の滞留、鍵のローテーション。いずれも今は手作業。運用画面を作るか、手順書で足りるか。

いずれも「直せない」ものではなく「今やるか、いつやるか」の判断katahimo-app
5つに絞りました。1番は設計の是非というより「この依存を許容するか」。2番は順序の問題です。3番が一番大きくて、予約や請求は後から足すとデータ移行が伴うので、土台のうちに入れるべきかを聞きたい。4番と5番は、どこまでをローンチの条件にするかという線引きです。私の推奨は、メールだけ別経路に逃がしたうえで、予約のスキーマを先に入れることです。ただしこれは意見なので、ご判断をいただきたい。

まとめ

この設計で守れていると考えているもの

  • core が外部SDKを知らない → Node とブラウザで同一コードが動く(デモで実証)
  • テナント分離の二重防御。効いていることを静的検査と実DBの両方で検証している
  • 揃って成立すべき書き込みが1つのトランザクションで確定する
  • 要配慮データの列暗号化、鍵の世代管理、暗号学的削除の導線
  • 認証の失敗経路(列挙・総当たり・割り込み・部分更新・クロスサイト)を塞いだ

判断をいただきたいもの

  • GAS ブリッジ1本への依存と、その運用設計
  • 鍵管理を本番相当にする時期
  • 予約・請求・カルテを土台に入れる順番
  • テストの薄い層と、運用の受け皿をどこまで作るか
