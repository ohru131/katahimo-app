# 目的

顧客カルテ・予約・請求と決済・訪問割当の最適化・移動手当・日報AIのプロンプト調整の
6ドメイン(28テーブル)について、設計意図と、**まだ決めきれていない論点**をまとめる。データベースの有識者レビューで
論点を絞っていただくための資料。

テーブル・列の一覧そのものは `doc/db/reference.md`(自動生成)、
テーブルの役割は `doc/db/overview.md` 第4章を参照。
このドキュメントは「なぜその形にしたか」と「どこに自信が無いか」に絞る。
データベース全体の設計指針と踏んだ落とし穴は `doc/db/guidelines.md` を参照。

# 0. 前提

- **本アプリはまだ実運用前。** 本番のPostgreSQLは存在せず、移行すべきデータも無い。
  スキーマは `packages/db/drizzle/0000_baseline_schema.sql` に、それ以降の差分マイグレーションを
  積み増して構成する(運用方針は `doc/db/overview.md` 第1.9節)。
- 現に本番稼働しているのは GAS 版(`reference/gas-childcare-visit-app`)で、本アプリは
  その移植先。給与計算(勤怠)は GAS 版と数値が1円も違ってはいけないという制約がある。
- これらのドメインは**スキーマ・制約・ドキュメントまで**を先に固め、有識者レビューを受けてから
  リポジトリ実装・API・画面を作る進め方を採っている。日報AIのプロンプト調整は
  リポジトリ実装・API・画面まで実装済み(第6章「実装済みの範囲」)、他のドメイン
  (顧客カルテ・予約・請求と決済・訪問割当の最適化・移動手当)はスキーマ・制約・ドキュメントの
  段階で、リポジトリ実装・API・画面はまだ無い(機能の実装は別途)。
- これらのテーブルはすべて既存と同じ方針に従っている: `tenant_id` + RLS(`tenant_isolation`
  ポリシー + `FORCE ROW LEVEL SECURITY`)、`(tenant_id, 参照先ID)` の複合外部キー、
  金額は円の整数、`updated_at` はDBトリガー。この4点は
  `packages/db/src/rlsPolicies.test.ts` と `packages/db/src/updatedAtTriggers.test.ts` が
  スキーマ定義から対象テーブルを自動で集めて検査するので、追加漏れはテストで落ちる。

## 0.1 区分値(CHECK制約の許可値)の置き場所

区分値は `packages/shared/src/contracts/` に zod の enum として置き、DBの CHECK 制約は
`packages/db/src/schema/_sqlLiteral.ts` の `sqlInList()` を通してその配列から組み立てている。

DDL に `IN ('a', 'b')` とベタ書きすると、区分が増えたときに DB だけ古い許可値のまま残り、
「アプリは通すのに DB が 23514 で拒否する(またはその逆)」というズレに気付けない。
配列を1箇所に置けば、区分の追加・削除が型と DDL の両方に同時に効く。

なお、CHECK 制約に**数値の定数**を入れるときは `sqlNumber()` を通す必要がある。
drizzle の `sql` テンプレートに JavaScript の値を `${}` で直接埋めるとリテラルではなく
バインドパラメータ(`$1`)になり、`CHECK (... <= $1)` という適用できない DDL が生成される
(実際にこれで「there is no parameter $1」を踏んだ)。

# 1. 顧客カルテ(`customer_notes` / `customer_note_photos`)

## 要件

顧客ごとに、カルテ(経過記録)・申し送り・鍵の位置・ガレージ場所・引き継ぎ事項・注意点を、
**写真付きで**残せるようにする。

## 設計

区分(`category`)を持つ1テーブルにまとめ、写真は子テーブルに持たせた。

- どの区分も「本文 + 写真 + 誰がいつ書いたか」という同じ形をしている。区分ごとにテーブルを
  分けると、写真テーブル・RLSポリシー・索引を区分の数だけ複製することになり、
  区分が増えるたびにマイグレーションが必要になる。
- `customers` の列(`key_location` など)にはしない。上書きになるため「いつ誰がその情報に
  したか」が残らない。鍵の位置やガレージの場所は現場で変わり、訪問前に読む情報が誤っていた
  ときに経緯を辿れないのは運用上の事故に直結する。
- 一覧画面は区分を横断して新しい順に出すため、`index(tenant_id, customer_id, created_at DESC)`
  が1本で足りる。
- `pinned`(常に上部に固定)を区分で代用しない。同じ区分の中にも「今も有効な注意点」と
  「過去の経緯として残す注意点」が混ざる。
- `resolved_at` / `resolved_by_staff_id` は必ず揃う(CHECK制約)。片方だけ入った行は
  「誰が閉じたか分からない」「閉じていないのに担当者だけいる」という読めない状態になる。
- 写真の実体はオブジェクトストレージに置き、DBは保存キー(`file_key`)だけを持つ。
  領収書画像(`receipts.file_key`)と同じ方式で、キーの命名も
  `{tenantId}/customer-notes/{uuid}.{ext}` と揃える。DBに `bytea` で入れないのは、
  バックアップとレプリケーションの容量が画像の枚数に比例して膨らむため。

## レビューで確認いただきたい点

1. **区分の粒度。** 「カルテ(経過記録)」は訪問のたびに積み上がるので件数が他の区分より
   桁違いに多くなる見込み。同じテーブルに置き続けてよいか、経過記録だけ別テーブルに
   分けるべきか(現状は `index(tenant_id, customer_id, category)` で絞れる前提)。
2. **本文が空の行を許している。** 鍵の位置・ガレージ場所は写真1枚で意味が通ることが多く、
   本文を必須にすると現場が意味のない文字を入れる。代わりに課したい条件
   「本文が空なら写真が1枚以上」は別テーブルの件数を参照するため1行のCHECK制約では
   書けず、入口(usecase)で担保する方針にしている。この判断が妥当か。
3. **写真の並び順に一意制約を付けていない。** 人が画面で2枚の `sort_order` を入れ替える操作を
   1本の UPDATE で書くと、PostgreSQL は一意制約を行ごとに即時検査するため必ず衝突して失敗する
   (回避には DEFERRABLE な制約が必要だが、drizzle のスキーマ定義では表現できない)。
   そのため一意制約は付けず、`ORDER BY sort_order, id` で並び順の決定性を担保する方針にした。
   同じ判断を `travel_legs.sequence` と `invoice_lines.line_no` には適用していない
   (どちらも人が1件ずつ並べ替えるものではなく、その日の分・その請求書の分をまとめて
   作り直す前提なので、一意制約で曖昧さと二重送信を止める方を取った)。この線引きが妥当か。
4. **写真の配信経路が未実装。** `StoragePort` の GCS 実装と署名付きURLの発行、
   `/api/files/:key` の配信は現状まだ無い(ローカル開発のファイルシステム実装のみ)。
   カルテ写真は要配慮性が高いので、署名付きURLの有効期限とアクセス制御の設計は
   実装前にレビューを受けたい。

# 2. 予約(RESERVA移植版)

`service_menus` / `reservations` / `reservation_assignments` / `staff_availabilities`。

## 設計

- **予約と日報(実施記録)を分ける。** 予約は「これから行う約束」、日報は「実際に行った
  ことの記録」で、片方だけ存在する状態が正常にあり得る(予約なしの緊急訪問、キャンセルで
  日報が無い予約)。1テーブルにまとめると「約束の時刻」と「実際の時刻」がどちらの意味なのか
  列ごとに変わり、集計が書けなくなる。紐付けは `daily_reports.reservation_id`(null許容)で持ち、
  1つの予約に日報が2件付かないよう部分一意索引を張っている(実施記録が重複すると
  サービス提供分の請求も二重になる)。
- **スタッフの割当を別テーブルにする。** 1予約に主担当+同行が付く運用があるため。
  `staff_id_1` / `staff_id_2` と列を増やす形にすると、人数が変わるたびにマイグレーションが
  必要になり「何人まで」をスキーマが勝手に決めてしまう(勤怠 `row_data` が訪問3件までに
  縛られている失敗を繰り返さない)。主担当が1予約に1人までであることは、
  `role='primary' AND unassigned_at IS NULL` の部分一意索引で保証する。
- **状態とタイムスタンプの整合を CHECK 制約で縛る。** `status IN ('cancelled','no_show')`
  であることと `cancelled_at IS NOT NULL` であることを同値にする、など。状態だけ進めて
  タイムスタンプを入れ忘れた行は「いつ確定したか」が分からず売上の計上月を決められない。
- **受付枠は繰り返し(曜日)と特定日を同じテーブルに入れる。** 「毎週火曜9-17時は受付可」に
  「今週の火曜だけ不可」を重ねる運用になる。テーブルを分けると判定のたびに2テーブルを
  突き合わせることになり、しかも「どちらが優先か」が読み手に伝わらない。
  `kind='unavailable'` が1件でも重なれば不可、という1つの規則にした。
  `weekday` と `specific_date` はちょうど一方だけを許す(両方入った行は
  「毎週火曜の、2026-04-20だけ」という読めない意味になる)。
- **RESERVA からの再取込を冪等にする。** `(tenant_id, external_source, external_id)` の
  部分一意索引で、同じ予約が二重に入らないようにする。

## レビューで確認いただきたい点(最も相談したい論点)

1. **ダブルブッキングをDBで止められていない。**
   「同じスタッフに時間帯が重なる予約を割り当てない」を DB で保証する正攻法は
   排他制約(`EXCLUDE USING gist (tenant_id WITH =, staff_id WITH =,
   tstzrange(start_at, end_at) WITH &&)`)だが、次の2つの事情で採れていない。
   - スカラー列の `=` を排他制約に混ぜるには `btree_gist` 拡張が必要。
     本番想定の PostgreSQL では `infra/initdb/01_bootstrap.sql` が作成しているが、
     **公開デモとテストが使っている PGlite(PostgreSQL/WASM)ではこの拡張が使えない**
     (実際に試して `extension "btree_gist" is not available` を確認した)。
     デモは「本番と同じマイグレーションをそのまま流す」ことでスキーマの正を1つに
     保っているので、本番だけ制約が増える形は、テストで検証できない制約を作ることになる。
   - 時間帯を持つのは `reservations` で、スタッフを持つのは `reservation_assignments`。
     排他制約は1テーブル内でしか書けないため、割当側に開始・終了時刻を複製する
     (非正規化する)必要がある。
   選択肢は (a) 割当側に時刻を複製して本番のみ排他制約、(b) plpgsql トリガーで重なりを
   検査(READ COMMITTED では同時挿入の競合を取り切れない)、(c) アプリ層で
   アドバイザリロックを取ってから検査、(d) 重なりを許して画面で警告するだけ。
   どれを採るべきかご意見をいただきたい。
2. **`transport_allowance_rules` の有効期間の重なりも同じ問題を抱えている**(下記5章)。
   1と同じ判断でよいか、それとも件数が桁違いに少ないので別扱いでよいか。
3. **取込元キーの片方だけが入った行を禁止した(対応済み)。**
   `(tenant_id, external_source, external_id)` の部分一意索引は、`external_source` が
   NULL の行同士を「別の値」として扱うため、`external_id` が同じでも2件通ってしまい
   RESERVA 再取込の冪等性が崩れる。そのため
   `(external_source IS NULL) = (external_id IS NULL)` の CHECK 制約を
   `reservations` と `service_menus` に張っている。
   なお `customers_tenant_external_idx` も同じ形の索引だが、こちらには対の CHECK が無い。
   同じ CHECK を足すべきかご意見をいただきたい。
4. **`staff_availabilities` の時刻を `time` 型にしている。** 日跨ぎの枠(22:00-01:00)は
   「その日の22:00-24:00」と「翌日の00:00-01:00」の2行で表す前提。
   夜間対応の運用が本格化したときにこの表し方で足りるか。

# 3. 請求と決済(Stripe)

`customer_payment_profiles` / `invoices` / `invoice_lines` / `payments` /
`stripe_webhook_events`。

## 設計

- **カード番号を受け取らず保存しない。** 保持するのは Stripe が返す識別子
  (`cus_...` / `pm_...` / `pi_...` / `ch_...`)と、画面表示用のブランド名・下4桁だけ。
  決済フォームは Stripe が提供するものを使い、PCI DSS の適用範囲を広げない。
- **Stripe の識別子を `customers` の列にしない。** Stripe は本番環境とテスト環境で顧客IDが
  別物になるため、顧客テーブルに1本だけ列を持つとテスト用IDで上書きして本番の紐付けを失う。
  また `customers` は RESERVA CSV の再取込で列を上書きする対象で、そこに決済の紐付けを
  混ぜると取込のたびに消える危険がある。
- **状態の語を Stripe に合わせる。** `invoices.status` は Stripe の Invoice status、
  `payments.status` は PaymentIntent status と同じ語を使う。独自の語にすると対応表を
  どこかに持つことになり、必ずズレる。現地現金決済(`onsite_cash`)は Stripe を通らないが、
  請求書に対する入金の有無を1箇所で見られるように同じテーブル・同じ語で扱う。
- **金額はすべて円の整数。** `numeric` や `double` にすると丸め方の違いで請求額と入金額が
  1円合わない事故が起きる。端数は税計算の時点で丸め、DBには丸め後の整数だけを入れる。
  通貨列を `'jpy'` に CHECK で固定しているのは、「将来通貨が増えるかも」ではなく
  「金額列が全て円の整数(小数を持たない)」という前提を通貨と一緒に読めるようにするため。
  円以外を足すときは最小単位の扱いを決め直す必要があるので、勝手に増やせないようにした。
- **請求書は合計を保存し、かつ内訳との一致を CHECK 制約で強制する**
  (`total = subtotal - discount + tax`)。合計は明細から計算できるが、請求書は
  「送付した時点の金額」が確定値であり、明細の追加・修正で過去の請求額が動いてはいけない。
  一方で内訳と合計がズレた行は読めないので、DBで縛る。
- **明細は必ず元データを指す。** `daily_report_id` / `receipt_id` / `coupon_redemption_id`。
  金額だけを持つ明細は、後から根拠を辿れず二重請求も検出できない。
  同じ領収書・同じクーポン適用が2つの明細に載らないよう部分一意索引を張っている
  (日報は「サービス提供分」と「移動手当」で複数明細に分かれるため一意にしない)。
  これは `coupons.ts` のコメントが「請求機能(`invoice_lines`)がまだ無いので割引後の
  請求額は保存しない」と書いていた、その `invoice_lines` に相当する。
- **割引明細の符号を種別で縛る。** `coupon_discount` は `amount_yen <= 0`。
  割引が正の数で入ると請求額が増える方向に転ぶため、DBで止める。
- **Webhook を冪等化する。** Stripe は「少なくとも1回」配信するので同じイベントが複数回
  届く。冪等化しないと1回の決済で `payments` が2行できる。
  `(tenant_id, stripe_event_id)` の一意制約で弾き、生の JSON を持っておいて
  失敗したイベントを Stripe に再送を頼まずに再処理できるようにする。

## レビューで確認いただきたい点

1. **Webhook のテナント特定。** すべてのテーブルを RLS で守る方針のため
   `stripe_webhook_events.tenant_id` も NOT NULL にしている。しかし Stripe から届く
   イベントには本アプリのテナントIDが入っていない。現状の方針は
   「受信口をテナントごとに分ける(URLにテナントを含める)か、イベント内の Stripe 顧客IDから
   `customer_payment_profiles` を逆引きする。どちらでも決められないイベントは記録せず拒否する」。
   拒否したイベントの記録がどこにも残らないことになるが、それでよいか
   (テナント不明のデータをどこかのテナントの中に置くよりは良い、という判断)。
2. **返金を `payments` の列(`refunded_amount_yen`)で持っている。** 複数回の返金の内訳が
   必要になったら明細テーブルを足す想定。最初から `refunds` テーブルにすべきか。
   現状の形の利点は、CHECK 制約で「元の決済額を超える返金」をDBで止められること。
3. **請求書番号(`invoice_no`)の採番をアプリでやる前提**にしている。
   テナント内で一意という制約はあるが、連番の穴あき(採番後にロールバック)は許容している。
   会計上これで問題ないか。
4. **請求書を void して再発行するときの扱い(方針を選んで実装済み。妥当性の確認をお願いしたい)。**
   同じ領収書・同じクーポン適用が二重請求されないよう `invoice_lines` に部分一意索引
   (`(tenant_id, receipt_id)` / `(tenant_id, coupon_redemption_id)`)を張っている。
   ところが索引の条件に別テーブル(`invoices.status`)を書けないため、素朴に張ると
   **void した請求書の明細も引き続き領収書を掴み**、誤請求を void して作り直した瞬間に
   23505 で弾かれる。そのため次の形にしている。
   - `invoice_lines.superseded_at`(nullなら有効)を足し、両方の索引の条件に
     `superseded_at IS NULL` を含めた。これで守るべき不変条件が
     「1つの領収書は**有効な**明細1つにしか載らない」という正しい形になる
     (元の索引は「1つの領収書は生涯1つの明細にしか載らない」を強制していて、
     これは void と再発行のある業務では単に誤り)。
   - void した請求書の明細に `superseded_at` を入れる責任は usecase に置いた
     (請求書を void にする操作が「`invoices` の更新 + 明細への `superseded_at` 設定」を
     同一トランザクションで行う)。DBのCHECK制約では別テーブルの状態を参照できず、
     トリガーを増やすよりも「void する経路が1つしかない」ことで担保するほうが
     追える、という判断。
   - 採らなかった選択肢: (a) void 時に明細を削除する — 何を void したかの内訳が失われる。
     (c) 二重請求の検出をDBではなくアプリだけの責務にする — この設計は
     「入口で見ていなかった値域をDBで縛る」(`doc/db/overview.md` 第1.6節)を方針にしているため、
     金額に直結する不変条件をDBから外すのは逆行する。
   この線引き(不変条件はDB、状態の同期は usecase)が妥当かご意見をいただきたい。
5. **`invoices` の明細合計と `subtotal_yen` の一致は DB で縛れていない**
   (別テーブルの集計を1行のCHECK制約では書けない)。請求書を確定する usecase 側で
   確認する方針だが、トリガーで縛るべきか。

# 4. 訪問割当の最適化パラメータ

`trait_definitions` / `customer_traits` / `staff_traits` /
`staff_customer_compatibilities` / `staff_customer_travel_estimates`。

## 設計

- **特性の項目自体をデータにする。** 何を見て最適化するかは今後のヒアリングで決まる
  (現時点で確定していない)。項目を `customers` / `staff` の列として足す設計にすると、
  項目が1つ増えるたびにマイグレーションと画面の作り直しが必要になり、現場からの
  「これも見てほしい」に追従できない。
- **それでも値を jsonb の塊にはしない。** 「この特性を持つ顧客の一覧」「この項目の分布」を
  SQL で素直に書けるようにするため、値の型ごとに列を分ける
  (`value_bool` / `value_int` / `value_text`)。どの列に入れるかは
  「ちょうど1つだけ非NULL」という CHECK 制約で縛る。
- **項目マスタは顧客とスタッフで共通、値のテーブルは分ける。** 相性判定では顧客側の特性
  (「犬がいる」)とスタッフ側の特性(「犬が苦手」)を突き合わせるので、項目マスタを分けると
  対応関係の管理が二重になる。一方、値を1テーブルにして `subject_id` を顧客IDと
  スタッフIDの兼用にすると、行ごとに参照先テーブルが変わるため外部キーを張れない。
  この設計は「RLS は FK 制約をバイパスするので、テナント越えの取り違えは複合FKで検知させる」
  という前提に立っているので、FK を張れない形は採れない。
- **相性のスコアと「絶対に組ませない」を別の列にする。** `score` は割当の優先度に使う
  連続的な値、`avoid` は候補から外す二値の判断。1つの数値に混ぜると
  「スコアが低いだけ(空きが無ければ許容)」と「絶対不可(空きが無くても割り当ててはいけない)」を
  区別できなくなる。苦情や事故が理由の `avoid` を、人員が足りない日に自動割当が押し通して
  しまうのは起こしてはいけない事故。`avoid=true` の行は理由(`reason`)を空文字にできない
  (後任者が理由を知らずに解除すると、避けていた事故が再発する)。
- **「まだ組んだことがない」は行が無い状態で表す。** 顧客数×スタッフ数の行を先に作ると、
  実際に評価された組み合わせと未評価の組み合わせを区別できなくなる。
- **スタッフ自宅↔顧客宅の距離を移動手段ごとに保存する。** 割当の最適化は
  「全スタッフ×その日の全訪問先」の総当たりになるため、その場で経路検索を呼ぶと
  呼び出し回数と待ち時間が実用にならない。住所が変わらなければ距離も変わらないので保存する。
  自動車で15分の距離が公共交通機関では50分になる、というのが割当判断の要点そのものなので、
  手段ごとに行を分ける。出発地のために `staff` に自宅住所と座標
  (`home_address` / `home_lat` / `home_lng`、`customers` と同じ `numeric(9,6)`)を足した。

## レビューで確認いただきたい点

1. **項目マスタ+値テーブル(いわゆる EAV)にしていること。** 項目が未確定という事情から
   選んだが、項目が固まった後もこの形を維持すべきか、固まった時点で列に移すべきか。
   移す場合の移行のしやすさも含めてご意見をいただきたい。
   なお「値テーブルが反対側の項目を参照できてしまう」問題(`customer_traits` の行が
   `subject_kind='staff'` の項目を指せる)は塞いである:
   値テーブル側に固定値の区別子列(`definition_subject_kind`)を持たせ、
   `(tenant_id, definition_subject_kind, definition_id)` で
   `trait_definitions(tenant_id, subject_kind, id)` を参照する形にした
   (`tenant_id` の取り違えを複合FKで防いでいるのと同じ手)。
2. **`match_weight` を `numeric(5,2)` でマスタに持たせている。** 重みをコードの定数にすると
   変更にデプロイが必要になるためデータにしたが、重みを変えると過去の割当結果を
   再現できなくなる。割当結果自体を保存するテーブル(「いつ・どの重みで・誰を割り当てたか」)を
   足すべきか。
3. **スタッフの自宅住所を平文で持つこと。** 本アプリはフィールド単位の暗号化を
   資格情報だけに縮小し、業務データは「DB/バックアップの保存時暗号化 + TLS + RLS +
   アクセス制御」で守る方針(`doc/db/overview.md` 第1.3節)。スタッフの自宅住所もこの方針の範囲内と
   判断したが、要配慮性の評価としてこれで妥当か。
4. **`staff_customer_travel_estimates` の再計算の運用。** `source='manual'`(実測値)は
   再計算で上書きしないという規則を持たせたが、これは DB では表せず usecase 側で守る。
   列で表すべきか(`locked` のようなフラグ)。

# 5. 移動手段と手当

`transport_allowance_rules` / `travel_legs`。

## 背景(実装の現状)

移動は自動車前提だった。確認した事実:

- `MapsPort.route()` に移動手段のパラメータが無く、GASブリッジ側が
  `Maps.DirectionFinder.Mode.DRIVING` を固定で使っている。
- 勤怠計算(`attendanceCalc.ts`)は距離から「基準距離超過回数」(15km超を5km刻みで数える
  中間値)と距離合計を出すところまでで、**金額への換算ロジックは本アプリにも GAS 版にも
  存在しない**。単価に相当する定数も無い。
- 勤怠の `row_data` は旧テンプレート(列記号 A,B,C…)由来の形で、移動を
  「通勤の距離」「訪問1の距離」…と最大2区間の固定枠でしか表せない。

つまり「移動手段により手当が変わる」は、既存ロジックの修正ではなく新規の追加になる。

## 設計

- **単価をデータで持つ**(`transport_allowance_rules`)。移動手段ごとに計算方法自体が違う
  (距離比例 / 1移動あたり定額 / 1日あたり定額 / 実費精算)ため、計算方法(`calc_kind`)も
  行が持つ。単価をコードの定数にすると値上げのたびにデプロイが必要で、しかも過去分を
  再計算すると支給済みの手当額が変わってしまう。
- **有効期間(`effective_from` / `effective_to`)を持つ。** 「4月から単価を上げる」を
  行の書き換えではなく新しい行の追加で表せるようにする。3月分の再計算は3月時点の行を引く。
- **移動区間を行にする**(`travel_legs`)。区間ごとに手段を記録し、区間ごとに手当を算定する。
  これは `doc/db/guidelines.md` §2 の段階2(勤怠の正規化)が向かう先でもある。
  当面は給与計算はこれまで通り `row_data` を入力に行い(GAS版との数値一致を崩さないため)、
  このテーブルは手当の算定と移動実績の記録に使う。
- **`attendance_days` への外部キーを張らない。** 移動区間は勤怠の行を作る前に記録されうる
  (訪問の合間に入力する運用)。対応付けは `(tenant_id, staff_id, business_date)` で行う。
- **手当額をスナップショットして持つ。** 単価マスタを後から書き換えても支給済みの手当額が
  動いてはいけない(クーポンの適用記録と同じ理由)。適用した規則のIDも併せて持ち、
  「なぜこの金額になったか」を辿れるようにする。金額と規則IDは必ず揃う(CHECK制約)。
- **距離はメートルの整数。** km の小数にしないのは丸め誤差を持ち込まないため(金額と同じ方針)。
- **移動手段に「徒歩」を含める。** 手当が付かない移動でも「自動車で行かなかった」ことは
  記録しなければならない(自動車前提の距離手当が誤って付くのを防ぐため)。
  手当が0円になるのは単価マスタに行が無い結果であって、列挙から外す理由にはならない。

## レビューで確認いただきたい点

1. **勤怠 `row_data` と `travel_legs` に距離が二重に存在する期間ができる。**
   GAS版との数値一致を崩さないために `row_data` を入力にした計算を残す判断だが、
   移行の段取り(いつ `row_data` の距離を捨てるか、その間の食い違いをどう検出するか)に
   ついてご意見をいただきたい。
2. **単価マスタの有効期間の重なりを DB で禁止していない**(理由は2章の論点1と同じ)。
   `(tenant_id, transport_mode, effective_from)` の一意制約までで、重なりの検査は
   登録時に行う方針。
3. **`per_day`(1日あたり定額)の計算単位が区間テーブルと合っていない。**
   `travel_legs` は区間ごとの行なので、1日あたりの手当をどの行に載せるかが決まらない
   (現状は「区間のどれかに載せる」でも「1日分の行を別に作る」でも表せてしまう)。
   日次の手当行を別テーブルにすべきか。
4. **`per_km` の手当に距離が入っていることを DB で縛れていない。**
   `travel_legs.distance_meters` は「自転車・徒歩でも距離は残す」ために null 許容にしたが、
   `calc_kind='per_km'` の規則を適用した行で距離が null だと手当額を算定できない。
   規則の種別は別テーブル(`transport_allowance_rules`)にあるため1行のCHECK制約では
   書けず、算定する usecase 側で担保する方針。列で縛る形(手当額と距離をセットで必須にする)に
   すべきか。
5. **公共交通機関の実費(`fare_yen`)を区間ごとに持っている。** 定期券区間は実費が
   発生しないため上限(`max_amount_yen`)で頭打ちにする想定だが、定期券の有無自体を
   スタッフ側に持つべきか(`staff_traits` で表せるが、手当計算が特性マスタに依存するのは
   筋が悪い可能性がある)。

# 6. 日報AIのプロンプト調整(`prompt_templates` / `report_*` / `customer_report_profiles`)

## 要件

- GAS版が「ＡＩプロンプト」シートで管理者に開放していた**プロンプト文面の上書き**を、
  本アプリでもテナントごとにできるようにする。テナントの版が無いキーは
  `packages/shared/src/promptDefaults.ts` の既定文面(GAS版 `DEFAULT_PROMPTS` の移植)へ
  フォールバックする。
- 保護者向けの日報文面を、**子の年齢帯・家庭の教育関心度・保護者のストレス度**で組み替える。
  家庭ごとに教育的な言葉(「敏感期」「感覚統合」等)を使う度合いが違い、保護者の負担が
  大きい家庭では教育語を止めてねぎらいに切り替える必要がある。
- キーワード表・判定基準・言い回しは法人ごとの育児観・営業方針を反映するので、
  **テナントごとに管理者が調整**できる形にする。
- どの文面・どの語で生成した日報かを**後から辿れる**ようにする(`doc/proposal/tech-stack.md` の
  「AIが生成した記録はモデル名・プロンプトのバージョンを残す」方針)。

## 3軸のモデル

| 軸 | 値 | 由来 | 置き場所 |
|---|---|---|---|
| 子の年齢帯 | 月齢(都度計算) | 世帯構成員の生年月日 `family_members.dob_date` と訪問日 | `report_age_bands`(帯の定義と行動語) |
| 教育関心度★ | 1〜5(高いほど教育語を使う) | 家庭ごとに管理者・担当者が付ける | `customer_report_profiles.education_level` |
| ストレス度 | 1〜5(低いほど負担が大きい) | 訪問ごとにスタッフが評価。GAS版から引き継いだPSI評価 | `daily_reports.stress_level` |

ストレス度は★より優先する。ストレス度ごとに「★を何段下げるか」「教育語を使ってよいか」
「管理者連絡を要するか」を `report_stress_levels` の3列に持たせ、コードが機械的に適用する
(`packages/core/src/domain/reports/promptAssembly.ts`)。文面の一節として書くと、文面の編集で
安全弁が外れるため。

使用可否の判定は `report_keywords` の行ごとに
「月齢が `[age_from_months, age_to_months)` に入る」かつ「引き下げ後の★が
`[education_level_min, education_level_max]` に入る」かつ「ストレス度が `stress_level_min` 以上」。
3条件を全部満たす語だけを候補としてプロンプトに提示し、AIにキーワード表を丸ごと渡さない。
プロンプトが短く安定し、候補が決定的になる(テストで固定でき、生成記録と突き合わせられる)。

## 設計

- **文面は版を積む(`prompt_templates`)。** 上書きせず `(tenant_id, key, version)` で追記し、
  有効版は最大 `version`。「既定に戻す」も既定文面を新しい版として積む。日報は
  `report_ai_generations.prompt_template_id` で使った版を指すので、版は消せない。
  テナントの版が無いキーはコードの既定文面(GAS版の `DEFAULT_PROMPTS` を移植したもの)へ
  フォールバックする。GAS版 `getPrompt` の「シートに無ければ既定」と同じ挙動。
- **文面のキーは区分値(`PROMPT_TEMPLATE_KEYS`)。** GAS版の6キーに、GAS版ではコードにベタ書き
  だった領収書OCRと、保護者向け文面の文体ルール(`daily_report_stance`)を足した。
  差し込み位置(`{anonymizedText}` `{timeInfo}` `{childContext}` `{keywordGuide}` `{toneGuide}`)も
  区分値として `PROMPT_PLACEHOLDERS` に置き、管理画面で「使える差し込み」を案内できるようにする。
- **判定基準はレベルごとに1行(`report_education_levels` / `report_stress_levels`)。** 1テーブルに
  軸の区分で混ぜず2表にした。ストレス度側だけが持つ3列(引き下げ幅・教育語の可否・連絡要否)を
  null 可の列にして「軸によって意味のある列が違う」状態を作らないため。
- **キーワード表(`report_keywords`)の `category` / `tone` は CHECK で縛らない。** テナントが自分の
  言葉で決める分類で、コードが分岐に使わない。縛ると分類を1つ足すたびにマイグレーションになる。
- **年齢帯と語の相性(`report_age_band_keywords`)は多対多。** 月齢の範囲だけでも候補は絞れるが、
  同じ月齢で使える語が多いとき、どれを先に提示するかの手がかりになる。
- **温かみ表現・避ける表現(`report_phrases`)は1表+区分。** どちらも「表現 + 意図 + 適用する
  ストレス度の範囲」という同じ形。避ける表現はストレス度に関わらず全日報に効くので、範囲は
  必ず 1〜5(入口の `phraseInputSchema` が狭い範囲を拒む。管理画面にも範囲の入力欄を出さない)。
- **未設定・未評価の既定は「安全側」と「標準」を使い分ける。** ★が未設定の家庭は★2(標準。
  `DEFAULT_EDUCATION_LEVEL`)を使う。大半の家庭が標準相当という想定で、設定していない家庭の
  日報だけ急に素っ気なくなるのを避けるため。一方ストレス度(PSI)が未評価の訪問は、教育語を
  使わず(候補は空)、温かみ表現も選ばず(どの度合いに向けた言葉かが決まらないため)、管理者連絡も
  要さない(スタッフが危険を見て評価したときだけ立てる印なので、未評価を危険と同じ扱いにすると
  連絡の意味が薄れる)。PSIだけ安全側に倒すのは、★の無評価は「教育語を使うかどうか」という
  文面の調整の話にとどまるのに対し、PSIの無評価は保護者の負担度合いが分からない状態そのもので、
  分からないときに教育語や決めつけた温かみ表現を選ぶ方が危ういため(`promptAssembly.ts` の
  `assembleDailyReportPrompt` のコメント参照)。
- **★は `customers` の列にしない(`customer_report_profiles`)。** `customers` は RESERVA CSV の取込で
  更新される「顧客側から来た情報」で、★は「こちら側の判断」。取込の全件上書きで消えては
  いけない。訪問割当の `customer_traits` にも載せない。あちらは「誰を組ませるか」の材料で、
  こちらは「どう書くか」の設定。目的が違う値を混ぜると、相性計算がうっかり★を読む余地が生まれる。
- **生成1回を1行で残す(`report_ai_generations`)。** モデル名・使った版・実際に送ったプロンプト全文・
  月齢・★(引き下げ前後)・ストレス度・入力メモ・AIの生の出力(または失敗理由)。`updated_at` を
  持たない事実の記録で、人が直した最終版は `daily_reports` 側。`daily_reports.ai_generation_id` が
  この表を指す(逆ではない)。生成は保存の前に何度でも行われ、保存に使われた1回だけが日報から
  参照される。日報が参照していない行(保存されなかった下書き)は、入力メモとAIの生出力を含むぶん
  日報本文より件数・容量が大きくなるため、既定365日(環境変数 `AI_GENERATION_RETENTION_DAYS`)を
  過ぎたらワーカー(`packages/worker`。`packages/core/src/usecases/reportAiRetention.ts`)が日次で削除する。
  日報から参照されている行は保持期間を過ぎても消さない(「なぜこの文面になったか」を辿る唯一の
  手掛かりのため)。
- **使った文面は版IDと全文の両方で残す(`report_ai_generations`)。** 使った版は `prompt_template_id`
  (既定文面なら NULL)、実際にモデルへ送った文字列は `prompt_text`。版IDだけでは復元できない。
  既定文面はコードのリリースで変わるうえ(そのときの文面はDBのどこにも無い)、3軸の差し込み
  (`{childContext}` `{keywordGuide}` `{toneGuide}`)の結果も版には残らないため。
- **提示した候補と使われた語を別表で残す(`report_ai_generation_keywords`)。** `output_json` を
  JSON検索して数える形にしないのは、語の廃止・改名(`report_keywords.active`)と突き合わせるのに
  外部キーが要るため。「提示したのに使われない語」「提示していないのに使われた語(創作)」を
  SQLで数え、表と文面の調整に使う。
- **`daily_reports` に2列を足した。** 主に描いている子 `target_family_member_id`(兄弟のいる世帯で
  「誰の日報か」を区別し、月齢の材料にする)と `ai_generation_id`。どちらも null 可で、
  GAS版から移す既存行はそのまま通る。複合FKは顧客IDまで含めた
  `(tenant_id, customer_id, xxx_id)` で張る(第1.2節の規約に、`daily_reports` が既に顧客IDを
  持っていることを足した形)。テナント内で別の家庭の子・別の家庭の生成を指せないようにするため。
  参照先として `family_members` に `(tenant_id, customer_id, id)`、`report_ai_generations` に
  `(tenant_id, customer_id, id)` の UNIQUE を置いた。`report_ai_generations.target_family_member_id`
  も同じ形で `family_members` を指す。

区分値と値域は `packages/shared/src/contracts/reportAi.ts`、組み立てロジックは
`packages/core/src/domain/reports/promptAssembly.ts`(純関数。テストで3軸の挙動を固定している)。

## 実装済みの範囲

`prompt_templates` のリポジトリ、テナントの版→既定文面のフォールバックで生成プロンプトを組み立てる
ユースケース(日報・事故報告・領収書OCR)、管理者API、設定モーダルの「AIプロンプト」画面(編集・版の
履歴・既定に戻す)、入力欄の入力例/記載要領の配信(GAS版 `getUiConfig` 相当)を持つ。

3軸(年齢帯・教育関心度★・ストレス度PSI)は、表(`report_*` / `customer_report_profiles`)のリポジトリ・
管理者API(`/api/settings/admin/report-ai/*`。年齢帯・キーワード・教育関心度・ストレス度・表現の
upsert と `POST .../import` によるxlsx取込のマージ)・管理画面(設定モーダル「日報AIの調整(3軸)」の
キーワード表/年齢帯/★/PSI/温かみ・避ける表現/取込の6タブ)・生成API・保存APIまで接続済み。

## レビューで確認いただきたい点

1. **月齢の範囲を半開区間 `[from, to)` にしている。** 「6〜12ヶ月」は from=6, to=12 で、
   12ヶ月ちょうどは次の帯(1歳)。年齢帯どうしの重なり禁止は1行のCHECKでは書けず
   (`btree_gist` の EXCLUDE は PGlite に無い。第7章1)、入口(usecase)で担保している。
   予約のダブルブッキング・移動手当単価の有効期間の重なりと同じ問題で、こちらも
   同じ判断(入口で担保)でよいか。

# 7. 全体を通しての論点

1. **`btree_gist` を使えないことによる制約の穴が3箇所ある**(予約のダブルブッキング、
   移動手当単価マスタの有効期間の重なり、日報AIの年齢帯どうしの月齢の重なり)。公開デモとテストが
   PGlite で動いていることと、「本番と同じマイグレーションをそのまま流す」ことでスキーマの正を
   1つに保つ方針の、どちらを優先すべきか。
2. **リポジトリ実装・API・画面を伴わないスキーマを先に入れている。** 使われない列が
   長く残るリスクと、DBの形を先にレビューできる利点のどちらを取るか。
3. **テーブルが44本ある。** マルチテナント+RLSの前提で、この規模を1つの
   PostgreSQL スキーマに置き続けてよいか(スキーマ分割やサービス分割の検討時期)。
4. **索引を「実際に発行するクエリ」から起こしているが、そのクエリがまだ存在しない**
   テーブルがある(予約・請求・最適化)。想定で張った索引が過剰でないか。
   なお `EXPLAIN` による確認(`Seq Scan` → `Index Scan`)は、この作業環境に
   PostgreSQL も Docker も無いため未実施(既存テーブルの索引も同じ状況)。
