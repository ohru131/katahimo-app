# 目的

データベースを触るときに守る決めごとと、実際に踏んだ落とし穴をまとめる。

- 現行スキーマそのものの解説 → `doc/09_データベース構造解説.md`
- 後から足したドメイン(カルテ・予約・決済・訪問最適化・移動手当)の設計判断とレビュー論点
  → `doc/15_追加ドメインの設計とレビュー論点.md`

この文書には「なぜその形なのか」と「同じ間違いを繰り返さないための注意」だけを置く。
値の正は常に `packages/db/src/schema/*.ts`(テーブル定義)と
`packages/db/drizzle/0000_baseline_schema.sql`(実際に適用されるDDL)にある。

# §1 金額は整数の円で持つ

金額列は `integer`(単位は円)で持ち、文字列や浮動小数では持たない。
`receipts.amount_yen` がその形で、取込元の表記(`"1,200円"` など)は `amount_raw` に残す。

- 文字列だと `SUM()` も範囲検索もできない。「集計・請求に使う」と決めた値が集計できない形で入るのは設計ミス
- 浮動小数を避けるのは丸め誤差を持ち込まないため

**解析できた値だけを型のある列に入れ、元の表記は `*_raw` に残す**というのが、このリポジトリ共通の形である
(`receipts.amount_raw` / `family_members.dob_raw` / `customers.lat_lng_raw` …)。取込元が自由記述で、
解析できない表記を捨てると情報が失われるため。

## 注意 — 重複判定キーには生の表記を使う

領収書の重複判定キーは取込時の生の表記から作っている。型を整えたついでにキーの材料を
`amount_yen` へ差し替えると、過去に積んだ冪等キーと食い違って二重登録が起きる。**キーの材料は触らない。**

# §2 勤怠 `row_data` の形

`attendance_days.row_data`(`jsonb`)は、1日分をまるごと読み書きする用途しか無く
`UNIQUE (tenant_id, staff_id, business_date)` で1行が特定できるため、**jsonb 1列で持つこと自体は妥当**。
ただし中身は意味のあるキーと数値で持つ。形は `packages/shared/src/contracts/attendance.ts` が正。

```
visits: [{ place, startTime, endTime, weatherAfter, plannedMoveMin, distanceKm }, …]
officeWork: [{ … }, …]
```

## 列記号キーにしてはいけない理由

以前はスプレッドシートの列記号(`C` / `D` / `AG` …)をキーにしていた。理由は
「GAS版と同じキー名なら、実データの数値照合を変換なしにできる」だったが、**手段の選び方が誤っている**。
照合は変換関数1本を通せば成立するので、そのために永続データの表現を犠牲にする必要が無い。
代償は照合が終わったあとも残る。

- 意味がデータベースから読めない(`"AG"` が何かはアプリのコードを読むしかない。社労士や監査に説明できない)
- 訪問3件・事務作業2件が構造的な上限になる。1日4件訪問した日を表現できない
- 元テンプレートの列構成が変わると、過去データのキーの意味が変わる

スプレッドシートのレイアウト由来の制約を、データモデルの制約に化けさせない。

## GAS版との数値一致は変換アダプタで守る

給与計算(`packages/core/src/domain/attendance/attendanceCalc.ts`)はGAS版と数値が1円もずれてはいけない。
そのため計算ロジックは列記号キーのオブジェクトを受け取る形のまま残し、
`packages/core/src/domain/attendance/columnRow.ts` が永続形式との相互変換を担う。
`fromColumnRow()` に本番の呼び出し元は無いが、**GASで検証済みの列記号ケースが永続形式を通っても同じ給与額になることを示す橋**なので消さない(同ファイルの先頭コメント参照)。

## 今後 — 段階2: 明細テーブルへの正規化(未実施)

現在の形は**段階1**(`jsonb` のまま、キーの意味と値の型だけを整えた状態)である。
実データ照合が終わったら `jsonb` をやめ、明細テーブルへ正規化する。方向は決まっているが、
**照合の基準を動かさないため照合後**に行う。

```sql
attendance_segments(
  tenant_id, id, attendance_day_id, seq,
  kind text,            -- 'visit' | 'office'
  place text, start_time time, end_time time,
  weather_after text, planned_move_min integer, distance_km numeric(6,2),
  UNIQUE (tenant_id, attendance_day_id, seq),
  FOREIGN KEY (tenant_id, attendance_day_id) REFERENCES attendance_days (tenant_id, id)
)
```

移動実績と手当の記録は、この正規化を待たずに `travel_legs` が受け持っている(`doc/15` §5)。

# §3 主要な検索経路には索引を張る

アプリが実際に投げる `WHERE` と `ORDER BY` の組に対して複合索引を張る。並べ替えの向き(`DESC`)も
`ORDER BY` と揃え、ソート自体を省けるようにする。`tenant_id` は RLS で必ず条件に入るので、
複合索引は `tenant_id` を先頭に置く。

一覧・削除の経路を索引だけで返せるかを基準にする(例: セッションの
`DELETE WHERE tenant_id = ? AND staff_id = ?`)。

---

# §4 値域はDBの CHECK 制約で縛る

区分値・範囲のある列には CHECK 制約を張る。入口(API)の検証とDBの制約は**両方**書く。
入口はユーザーに分かるエラーを返すため、DBは最後の砦(`psql` から直接書かれても守る)。

許可値そのものは `packages/shared/src/contracts/` の Zod スキーマが単一の正で、
`packages/db/src/schema/_sqlLiteral.ts` の `sqlInList()` 経由でDDLに展開する。
DDLに値を書き写さないのは、契約側から値が増減したときにDDLだけ古いまま気付けないため。

日本語の表示文字列(`'事故報告'` など)をそのままキーとして保存しているのは、GAS版のシートへ
同じ値を書き戻す必要があるため。コード化(`accident` / `near_miss`)は
スプレッドシート連携を終了する段階で行う。値域を縛ることとコード化は別の話なので、混ぜない。

検証は `packages/demo/src/checkConstraints.test.ts` と
`packages/demo/src/newSchemaConstraints.test.ts` が、本番と同じマイグレーションを当てた
PGlite上で「正常値は通る」「不正値は拒否される」の両方を見る。拒否側は**エラーメッセージに
制約名が含まれることまで確認する**(NOT NULL や FK など別の理由で偶然拒否されて、
何も検証していない状態にならないようにするため)。

# §5 `updated_at` はDBトリガーが更新する

`updated_at` 列を持つテーブルには `set_updated_at()` の `BEFORE UPDATE` トリガーを張る。
アプリのコードで `.set({ updatedAt: new Date() })` を書く方針は採らない。

- トリガーが常に `now()` を入れるため、アプリから明示指定しても上書きされる。これは意図した挙動(唯一の正をDBに置く)
- 張り忘れは `packages/db/src/updatedAtTriggers.test.ts` が落とす。対象テーブルをベタ書きせず、
  Drizzleスキーマのexportから `updated_at` 列を持つテーブルを動的に集める
  (ベタ書きの一覧だと、一覧の更新し忘れ自体がトリガーの張り忘れと同じ壊れ方をしてしまう)

## なぜアプリ側での更新が危険か

スプレッドシートへの書き戻しジョブの冪等キーは更新時刻から作られている
(`packages/core/src/domain/mirror/idempotencyKey.ts` の `revision = record.updatedAt`)。
UPDATE 経路を足したときに `updated_at` のセットを書き忘れると、冪等キーが前回と同一になり、
`UNIQUE (tenant_id, idempotency_key)` に弾かれて**ジョブが積まれず、編集内容が永久にミラーされない**。
しかもエラーにならないため気付けない。

実際に `customers` で書き忘れが起きており(`customerRepository` に `updatedAt` の文字列が1つも無く、
`updated_at` が行の作成時刻で止まっていた)、これがトリガー化の直接の動機である。

各リポジトリの `.returning()` がDBの返した行から `updatedAt` を読んでいることも守ること
(冪等キーの材料がトリガーの `now()` と食い違わないため)。

# §6 日付・時刻は型のある列で持つ

| 列 | 型 |
|---|---|
| `family_members.dob_date` / `accident_reports.target_dob_date` | `date`(+ `*_raw` に元表記) |
| `daily_reports.started_at` / `ended_at` | `timestamptz` |

- 文字列だと年齢の算出・年代別の集計・滞在時間の計算がSQLでできず、`"1990/13/45"` も保存できてしまう
- **未入力は `NULL`**。空文字と型で区別する
- 日跨ぎ勤務(`22:00`〜翌 `01:00`)が計算できることをテストで固定してある
  (`packages/demo/src/typedColumns.test.ts`)
- スプレッドシートへ書き戻す `"HH:mm"` 表記はミラー時に整形する。保存はしない

`daily_reports.occurred_at`(並べ替えキー)と `started_at` は同じ情報になりうるため、
`usecases/reports.ts` の `saveDailyReport` が `parseJstDateTime` を呼び直さず**同じ Date を共有する**。
二重に解析すると食い違いを作れてしまう。

# §7 緯度経度は数値2列で持つ

`customers.lat` / `customers.lng` を `numeric(9, 6)`、解析できない表記は `customers.lat_lng_raw` に残す。
CHECK で緯度 -90〜90・経度 -180〜180 を縛る。

- `numeric(9,6)` は小数第6位(約10cm)まで保持でき、国内の座標に十分。浮動小数を避けるのは §1 と同じ理由
- 座標は仙台市への報告(住所の座標化)・将来のジオフェンス・移動距離の算出に使う前提なので、
  `"38.26, 140.87"` のような1本の文字列では用を成さない
- 解析できない値・値域外の値は `lat`/`lng` を null にして `lat_lng_raw` にだけ残す(DB制約に違反する値を渡さない)
- PostGIS の `geography` 型は、距離計算をDB側で行う段階になったら検討する(いまは過剰)

ポート型(`CustomerRecord`)は `number | null`。`numeric(9,6)` の値域は倍精度で正確に表現できる範囲に
収まるため、境界で数値化してもデータは失われない。

# §8 踏んだ落とし穴

同じ失敗を繰り返さないために残す。いずれも実際に起きたもの。

## §8.1 Drizzle の `text({ enum: [...] })` は CHECK 制約を生成しない

これは TypeScript 上の型付けにすぎず、DDLには何も出ない。`psql` から `status='でたらめ'` を書けるし、
書けばワーカーが永久に拾わない行になる。**値域を縛りたいなら `check()` を明示的に書く。**

スキーマのコメントに `'事故報告' | 'ヒヤリハット'` と書いてあるのに、TypeScript の型は `string`、
入口の検証は `typeof body.reportType === 'string'`、DBの制約は無し、という
「3層すべてで値域を見ていない」状態が実在した。コメントは制約ではない。

## §8.2 `sql` テンプレートに JavaScript の値を埋めるとバインドパラメータになる

```ts
sql`${t.byteSize} <= ${MAX_BYTES}`   // → CHECK (... <= $1) が生成される
```

CHECK 制約はDDLなのでバインドパラメータを取れず、マイグレーションが
`there is no parameter $1` で落ちる。**定数は必ず `packages/db/src/schema/_sqlLiteral.ts` の
`sqlNumber()` / `sqlInList()` を通す**(`sql.raw()` でリテラルに展開される)。

## §8.3 NULL に評価される CHECK 制約は「通った」ことになる

PostgreSQL は CHECK が `false` のときだけ拒否する。`NULL` は満たされたものとして扱われる。

```sql
-- 悪い例: choices が NULL だと jsonb_typeof(NULL) が NULL になり、式全体が NULL → 素通り
CHECK ((value_type = 'choice' AND jsonb_typeof(choices) = 'array') OR (value_type <> 'choice' AND choices IS NULL))
```

`IN` も同じ罠にかかる。`NULL IN ('a', 'b')` は `false` ではなく `NULL` になる。

```sql
-- 悪い例: birthday_subject が NULL だと NULL IN (...) が NULL → 式全体が NULL OR false = NULL → 素通り
CHECK ((eligibility_kind = 'birthday_month' AND birthday_subject IN ('customer', 'family_member', 'any'))
    OR (eligibility_kind <> 'birthday_month' AND birthday_subject IS NULL))
```

NULL を取りうる列を CHECK に書くときは、**各枝に `IS NOT NULL` を明示する**。
「制約を書いたのに弾かれない」ときは、まずこれを疑う。この2例はどちらも実際に素通りさせて、
テスト(`packages/demo/src/newSchemaConstraints.test.ts`)で気付いた。

## §8.4 一意制約は行ごとに即時判定される

`UNIQUE (parent_id, sort_order)` のような列を持つと、**2行の値を入れ替える UPDATE が必ず衝突する**
(1行目を更新した時点で2行目とぶつかる)。`DEFERRABLE INITIALLY DEFERRED` なら避けられるが、
Drizzle のスキーマでは表現できない。

そのため `customer_note_photos.sort_order` には一意制約を張っていない。並び順の決定性は
`ORDER BY sort_order, id` で担保する。一方 `travel_legs.sequence` / `invoice_lines.line_no` は
まるごと作り直す運用なので一意制約を張っている。**「並べ替えが起きるか」で判断する。**

## §8.5 索引や制約の有無を「作成した箇所」だけで判断しない

「重複した索引が2本ある」と指摘して着手したところ、片方は後続のマイグレーションで
`DROP INDEX` 済みで、実際には1本しか無かった。マイグレーションは追記式なので、
`CREATE` と `DROP` を出現順に畳み込んだ**最終状態**を見る必要がある
(`packages/db/src/rlsPolicies.test.ts` と `updatedAtTriggers.test.ts` がまさにその方式)。

いまはマイグレーションが1本に統合されているため畳み込みは自明だが、
`0001` 以降を足したあとは再びこの注意が効いてくる。

## §8.6 部分一意索引は NULL を別物として扱う

`UNIQUE (tenant_id, external_source, external_id)` は `external_source` が `NULL` の行同士を
重複と見なさない。取込のべき等性を一意索引で担保するつもりなら、
**「両方 NULL か、両方値が入っているか」を CHECK で縛る**必要がある
(`reservations_external_pair_check` / `service_menus_external_pair_check` がその形)。

## §8.7 PGlite に無い機能を前提にしない

公開デモとテストは PGlite(WebAssembly 版 PostgreSQL)で本番と同じマイグレーションを流す。
そのため**本番の PostgreSQL では使える機能でも、PGlite で動かないものは採用できない**。

- `btree_gist` は利用できない(実機確認済み: `extension "btree_gist" is not available`)。
  そのため予約の二重取りを `EXCLUDE USING gist (... WITH &&)` では防げない(`doc/15` §2 の論点)
- 逆に `CREATE FUNCTION ... LANGUAGE plpgsql` + `BEFORE UPDATE` トリガーと、
  日本語リテラルを含む `CHECK (col IN ('事故報告', …))` は動作を確認済み

新しいPostgreSQL機能を使う前に、PGlite で動くかを先に確かめる。

# §9 割引クーポン(`coupons` / `customer_coupons` / `coupon_redemptions`)の設計判断

## 3つのテーブルの役割

| テーブル | 持つもの |
|---|---|
| `coupons` | 種別マスタ。何円引きか・いつ使えるか・誰が使えるか・何回使えるか |
| `customer_coupons` | 顧客への配布。`coupons.audience = 'assigned'` のクーポンを誰に配ったか |
| `coupon_redemptions` | 適用記録。どの日報に付けたか+適用時点の割引条件のスナップショット |

## 「誰が・いつ・何回使えるか」を3つの独立した列で表す

| 列 | 値 | 意味 |
|---|---|---|
| `audience` | `all` / `assigned` | 全顧客が使えるか、配った顧客だけか |
| `eligibility_kind` | `manual` / `birthday_month` | 条件なしか、対象者の誕生月だけか |
| `usage_limit_kind` | `unlimited` / `once_per_customer` / `once_per_customer_per_year` | 同じ顧客が何回使えるか |

3つは互いに独立なので、組み合わせるだけで「誕生月に年1回、全顧客が使える」「特定の顧客に
配った1回限り」のどちらも表せる。**条件式を JSON で持つ汎用のルールエンジンにはしない**
(DBが中身を検証できない列を増やすだけになる。§2と同じ理由)。条件が増えたら enum を増やす。

判定は全て `packages/core/src/usecases/coupons.ts` の `evaluateCouponEligibility` に寄せてあり、
日報画面の選択肢づくりと保存時の検証が**同じ関数を通る**。片方だけを直して「選べるのに保存
できない」組み合わせを作らないため。

## 誕生月の判定

`birthday_subject` が `customer` なら `customers.dob_date`、`family_member` なら
`family_members.dob_date`、`any` ならどちらでも見る。**年は見ず月だけを比べる**(「毎年その月」が
誕生月割引の意味のため)。生年月日を解析できなかった人(`dob_date` が NULL。§6)は対象外になる。

適用時には、根拠にした人の**氏名と生年月日を適用記録に写す**。「なぜ3月の訪問に誕生月割引が
付いたのか」に後から答えられるようにするため(請求の問い合わせ対応)。`family_members` への
外部キーにはしない — 世帯構成員は顧客の更新・再取込のたびに全件入れ替え(delete + insert)
される行で、IDが安定しないため。

`customers.dob_date` は RESERVA CSV に列が無く、画面からの手入力でしか入らない。そのため
**取り込み(`dob` を渡さない更新)では列に触らない**ようにしてある
(`buildCustomerRecordFields`)。ここを素通りさせると、再取込のたびに手入力した生年月日が
消えて、誕生月クーポンが翌月から無言で効かなくなる。

## 使用上限をDBで縛るために顧客IDを持たせた

| 論点 | 決定 | 理由 |
|---|---|---|
| クーポンを列(`daily_reports.coupon_code`)で持つか、テーブルにするか | **テーブル** | 1回の訪問に複数のクーポンを適用しうる。列だと1つしか持てず、あとから増やせない |
| 顧客IDを `coupon_redemptions` に持たせるか | **持たせる**(複合FKで縛る) | 「年1回まで」を一意索引で守るには、適用記録の行だけで顧客が分かる必要がある(一意索引は他テーブルを参照できない)。二重管理にならないよう `(tenant_id, daily_report_id, customer_id)` で `daily_reports` を参照し、日報の顧客と違う値が**物理的に入らない**ようにしている |
| 使用上限をどう数えるか | `usage_scope_key`(`lifetime` / `2026`)+ 部分一意索引 | 上限なしの行は NULL にして索引の対象外にする(§8.6)。年は適用日時ではなく**訪問日**から決める(年末の訪問を年明けに入力すると別の年に数えられてしまう) |
| 顧客ごとの配布を `coupons` の行を増やして表すか | **別テーブル**(`customer_coupons`) | 種別(何円引きか)と配布先(誰が使えるか)は別の情報。同じ内容のクーポン行とコードを顧客の数だけ作ることになる |
| 配布を取り消すときに行を消すか | **消す** | この表は「今この顧客が使えるか」を引くためのもので履歴ではない。使った事実は `coupon_redemptions` 側に残り、そちらは `coupon_id` を直接参照していてこの表を経由しない |
| 割引後の請求額を保存するか | **保存しない** | 算定基礎(単価・時間)は請求機能(`invoice_lines`)が持つ。ここで重複して持たない |
| クーポンを廃止したときに行を消すか | **消さない**(`active = false`) | 過去の適用記録から参照されている。消すと履歴が壊れる |
| 適用記録に割引条件を写すか | **写す** | 請求に使う値なので、マスタの書き換えで過去の記録が動いてはいけない |

上限は usecase でも見ているが、検索と登録の間をすり抜ける同時リクエストがあるため、
DB側の部分一意索引 `coupon_redemptions_usage_scope_uidx` を最後の砦として置いている(§8.4)。

# §10 領収書(実費報告)の請求区分と取り消し

## 請求区分(`receipts.billing_type`)

「ガレージ代など、顧客に請求する分と会社が立て替える分を分けたい」という要望から、
`receipts.billing_type` に `'customer_billable'`(顧客に請求する)/ `'company_expense'`(会社が立て替える)
を持たせている。許可値は `packages/shared/src/contracts/` 側が正で、CHECK 制約で縛る(§4)。
既定は `company_expense`。取りこぼし(スタッフが選び忘れた場合)が「うっかり顧客に請求してしまう」
方向に転ばないようにするため。顧客に紐付かない領収書は `customer_billable` にできない
(`receipts_billable_requires_customer`)。

請求書に載せる側は `invoice_lines.kind = 'receipt_billable'` が受け取る(`doc/15` §3)。

## 訂正は「編集」ではなく「取り消して登録し直す」

| 論点 | 決定 | 理由 |
|---|---|---|
| 金額・店舗名・顧客の紐付けを後から直せるようにするか | **しない** | 会計の記録なので、いつ誰がいくらに変えたのかが残らない形にしない。書き換えの経路そのものを作らない |
| 間違えたときの訂正手段 | **取り消して登録し直す** | 取り消した行と新しい行の両方が残る。スタッフから見た使い勝手は「消せる」のと変わらない |
| 取り消しを物理削除にするか | **しない**(`cancelled_at` を立てる) | 「あったはずのものが痕跡なく消える」状態を作らない。一覧にはグレーで残す |
| 取り消せる期間 | **領収書の日付 + 2日**(暦日)。ただし**その月の末日まで** | 締めたあとの月の記録が動くと会計が合わなくなる。期限は画面(ボタンを出さない)とサーバーの両方で見る |
| 管理者にも期限を適用するか | **しない** | 経理が締め処理で戻すことがある。期限は「日が経ってから記録が動く」のを現場側で防ぐためのもので、その判断ができる管理者まで縛る理由が無い |
| 取り消しの理由 | **任意の1行**(`cancellation_reason`) | 入力を必須にすると、急いでいる現場で形だけの文字列が入るだけになる |
| 取り消した人 | **必ず残す**(`cancelled_by_staff_id`) | 会計の記録として「誰が取り消したか」は要る。`receipts_cancellation_pair_check` が、取り消し済みなのに取り消した人が無い行を拒否する |
| 集計・出力 | **取り消し済みを除外する** | 一覧の合計、ミラー送信(`mirrorWorker` の `receipt`)のどちらも、送る直前に `cancelled_at` を見る |
| ミラー送信をいつ始めるか | **取り消せる期間が終わった直後** | 下記 |

### 取り消した行を重複判定から外す

`receipts_tenant_dedupe_key_uidx` の条件には `AND cancelled_at IS NULL` が入っている。

顧客の紐付けだけを間違えた場合、訂正は「取り消して、**金額も店舗名も日時も同じ**領収書を
もう一度登録する」ことになる。`dedupe_key` は正規化した金額+店舗名+日時から作るので完全に一致し、
取り消した行を索引の対象に残したままだと 23505 で弾かれて訂正できない。
`invoice_lines` の `superseded_at` 付き部分索引(void した請求書を作り直せるようにするためのもの)
と同じ理由・同じ形。

### ミラー送信は取り消し期限まで待つ

スプレッドシートへの追記は、**送ってしまうと取り消してもあちら側に残る**。一方で
「送る直前に `cancelled_at` を見る」だけでは、確認したあと送信するまでの間に取り消しが
確定する隙間が残る(外部へのHTTP送信をDBトランザクションに入れることはできないので、
この隙間はチェックの置き場所を変えても無くならない)。

そこで**送信そのものを取り消せる期間の後ろにずらす**。領収書の outbox ジョブは
`next_attempt_at` に `receiptMirrorSendAfter()`(= 取り消せる最終日の翌日0時・JST)を入れて
積むので、ワーカーはそれまでジョブを拾わない。**期限内の通常の取り消し**は必ず送信より前に
起きることになり、この経路では競合そのものが無くなる。

### 管理者の期限後取り消しだけは、送信後になりうる

上の保証が効くのは期限内の取り消しだけで、**管理者の `ignoreDeadline` はこの外にある**
(経理が締め処理で戻すために残してある例外)。期限後ということは送信開始時刻も過ぎているので、
そのときスプレッドシートには既に行が出ている。`mirrorWorker` の `cancelled_at` チェックは
送信前のジョブしか弾けないため、ここは仕組みでは塞げない。

塞ぐには「あちら側の行を取り消す」補償ミラーを積む必要があるが、**Bridge.js に領収書を
取り消す action が無い**(書き込み系は `writeReceipt` など追記のみで、追加はGAS側の
デプロイ承認が要る)。それが入るまでの間は、せめて**黙って成功にしない**という扱いにしている。
`cancelReceipt` は取り消しを確定させたあとに outbox の状態を引き、`done`(送信済み)または
`processing`(送信中で、送られたかどうか外から判別できない)なら `mirrorAlreadySent: true` を返す。
画面はそれを受けて「シート側の行は手で取り消してください」と出す。

**月をまたがない**ことがこの設計の要になっている。取り消し期限を月末で打ち切っている
(`receiptCancellableUntil`)ため、送信開始も必ずその月内〜翌月初に収まり、9月分の領収書が
10月の締めのあとに送られることはない。月末近くの領収書は、そのぶん取り消せる期間が短くなる
(9/30の領収書はその日のうちだけ)。これは「月末で締める」という会計側の要件から来る意図した挙動。

### 送信待ちが見えるようにする

この作りでは「登録したのにまだスプレッドシートに出ていない」期間が必ず発生する。管理者が
それに気付けないと、締めのときに送信が止まっていることが分からない。そのため領収書一覧は
`outbox_jobs` の状態を引いて、**未送信の件数・送信予定時刻・送信に失敗した件数**を出す
(`listStatusByTargets`。索引は `outbox_jobs_tenant_kind_target_idx`)。

### 期限を暦日で数える理由

**訪問保育は土日祝日も訪問がある。** 平日だけの業務ではないので、営業日(土日祝を除く)で
数えると、金曜の領収書だけ期限が火曜まで延びる一方、土日に訪問したぶんの期限は延びない、
という曜日によって扱いが変わる状態になる。そうする理由が業務側に無いため、暦日で数える
(`addDaysToJstDateKey`)。祝日カレンダーも要らなくなる。

期限の基準日は `receipt_timestamp` の日付(JST)。領収書には訪問日そのものを持っていないため
(OCRが読んだ領収書の日付、読めなければ登録時刻が入る)。
